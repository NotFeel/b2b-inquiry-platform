# b2b-inquiry-platform 前台页面优化与技术改造执行手册

- **文档类型：** 可执行开发任务与验收标准
- **状态：** 待评审、待实施；本文不代表代码已经修改或测试已经通过
- **版本：** 1.0
- **日期：** 2026-10-18
- **适用项目：** `b2b-inquiry-platform`
- **主要目标：** 改善品牌表现、产品发现、工厂信任建设与 WhatsApp 询盘转化

> 本文将前台重设计方案拆成可分配给开发人员的任务。任何建议路由、字段、组件名和 API 均不是对当前代码的事实断言。开始开发前必须先核实仓库、现有页面、API、Prisma Schema、存储和测试，再按最小改动原则实施。

## 1. 项目目标与范围

### 1.1 产品定位

将前台调整为更有品牌个性、年轻、友好但仍适合海外 B2B 客户的轻量外贸品牌官网。

品牌体验方向：

**Cute Products. Real Factory. Easy WhatsApp Inquiry.**

主要转化路径：

1. 访客进入首页，理解品牌和主要产品。
2. 浏览品类、搜索产品或查看精选产品。
3. 进入产品详情，查看真实图片、规格和包装信息。
4. 将单个或多个产品加入询价清单。
5. 生成包含产品名称、SKU、链接和数量的 WhatsApp 消息。
6. 访客在 WhatsApp 中确认并主动发送消息。

### 1.2 必须保留的现有能力

- `zh-CN`、`en-US` 中英文体验。
- 产品目录、产品详情、产品图库、规格、包装、标签、发布状态和生命周期。
- 多级品类导航。
- 单品 WhatsApp 联系与批量询价清单。
- 工厂照片、视频、生产流程、证书和荣誉等内容。
- 现有后台内容维护、角色权限、审计和文件存储机制。
- 内部报价价格不得泄漏到公开页面或公开 API。
- 产品/媒体数据以数据库和后台配置为准，不用前端硬编码假数据代替生产数据。

### 1.3 明确不做

- 不增加在线支付、购物车结算、会员积分或促销倒计时。
- 不因视觉重设计重写现有业务 API 或数据库模型。
- 不擅自更换技术栈、路由机制、i18n 方案、上传服务或权限体系。
- 不虚构工厂规模、产能、客户、认证、奖项或产品数据。
- 不把“点击 WhatsApp”统计成“询盘已发送”。
- 不将方案、代码生成或文档完成描述为已上线或测试通过。

## 3. 设计系统与视觉规范

以下数值为初始建议，需结合现有 Logo、真实产品图和对比度测试校准。

### 3.1 色彩令牌

| Token 建议名 | 初始值 | 用途 |
|---|---|---|
| `--color-page` | `#FFF8F1` | 页面暖白背景 |
| `--color-surface` | `#FFFFFF` | 卡片、弹层、内容面板 |
| `--color-pink` | `#F5B7CF` | 局部品牌装饰、分类卡片 |
| `--color-mint` | `#BDE9D0` | 工厂、品质相关区块 |
| `--color-yellow` | `#FFC96B` | 局部强调、亮点标签 |
| `--color-lavender` | `#C9C6FF` | 局部分类/装饰背景 |
| `--color-text` | `#453B4A` | 标题和正文 |
| `--color-muted` | 依据现有对比度测试确定 | 次要说明 |
| `--color-whatsapp` | 选择通过对比度测试的品牌绿色 | WhatsApp CTA |

规则：

- 暖白为主要背景，产品和工厂真实照片承担主要视觉重量。
- 粉色、薄荷绿、薰衣草紫只作辅助，不要每个区块都使用不同的强色。
- WhatsApp CTA 要醒目且易辨识。
- 状态不能只靠颜色表达，必须有文本或图标。
- 所有文本、按钮、焦点状态需检查对比度。

### 3.2 排版、尺寸与间距

| 元素 | 建议起点 |
|---|---|
| 英文标题字体 | Nunito 或项目已有的圆润友好字体 |
| 正文字体 | Inter 或系统无衬线字体 |
| 桌面主标题 | 40–52px |
| 移动端主标题 | 30–36px |

| 动效 | 短、轻、非阻塞；尊重 `prefers-reduced-motion` |

- Footer

- Product Card
- Product Gallery
- Product Status Badge
- Quantity Control
- Inquiry List / Inquiry Summary
- WhatsApp CTA
- Empty State / Loading State / Error State
- Breadcrumb
- Search and Filter Controls

每个可交互组件应具备：明确的可访问名称、键盘操作、加载/错误反馈、移动端样式和对应测试。

## 4. 页面改造规格

## 4.1 首页 Home（P0）

### 页面顺序

1. Header：Logo、主导航、语言切换、WhatsApp CTA。
2. Hero：品牌主张、简短价值说明、主视觉、两个主要 CTA。
3. Category Cards：主要产品分类入口。
4. Featured Products：少量精选产品。
5. Meet Our Factory：工厂视频封面或真实照片。
6. Quality & Awards：经核验的品质/荣誉信息。
7. How to Inquire：简单说明询价步骤。
8. Final CTA：咨询产品或定制。
9. Footer：联系方式、产品分类、品牌信息、FAQ、隐私政策和社交链接。

### 调整要求

- 首屏让用户快速理解“做什么产品、能否承接 B2B 询盘、如何联系”。
- Hero 的主要 CTA 为浏览产品；次要 CTA 为 WhatsApp 联系或询价。
- 精选产品必须来自真实发布数据，不能把 Demo 产品当成正式内容。
- 不在前台显示内部报价。
- 避免 Featured、New Arrivals、Pre-order 等区块无业务规则地重复展示同一产品。
- 分类名称、数量复数和按钮文案必须通过 i18n 资源维护。
- 工厂/证书区块没有真实素材时，不展示虚构信息；可隐藏区块或显示经批准的替代内容。
- 页脚邮箱、地址、电话和 WhatsApp 号码必须来自经过核验的配置。

### 验收标准

- [ ] 首屏有清晰品牌主张和主要 CTA。
- [ ] 主要 CTA 指向实际存在且正确的页面/流程。
- [ ] 产品、分类和媒体数据来自真实 API/内容源。
- [ ] 不出现 Demo 名称、占位图、示例邮箱或占位地址。
- [ ] `zh-CN`、`en-US` 的导航、标题、CTA 和内容语言一致。
- [ ] 390px 手机视口下首屏无水平溢出，CTA 可点击。

## 4.2 产品目录 Products（P0）

### 页面结构

- 页面标题和简短说明。
- 搜索输入与明确的提交/清除行为。
- 分类筛选；标签筛选（仅当当前业务确实需要）。
- 排序选项（沿用现有支持项）。
- 产品结果数量、产品卡片网格和分页。
- 批量询价入口与已选数量。
- 加载、空结果、错误和无匹配结果状态。

### 产品卡片内容

- 主图、产品名称、SKU（如符合当前展示策略）、关键短描述。
- 生命周期/发布相关标签（仅展示允许公开的状态）。
- “View Details” 与“Add to Inquiry”操作。
- 不显示内部价格。
- 图片缺失时使用统一 fallback，不显示破图图标。

### 交互规则

- 搜索框与图标按钮的职责清楚：图标若为提交按钮，应有可访问名称；若仅展开移动搜索，则行为要明确。
- 筛选变更后更新列表和结果数量，分页回到合理位置。
- 切换页码后已选产品不应无故丢失。
- 已停产/未发布产品遵循服务端发布规则，不由前端自行猜测可见性。
- 产品卡片的询价按钮不能意外触发卡片导航。

### 验收标准

- [ ] 搜索、筛选、排序和分页组合可工作。
- [ ] 结果数量与实际结果一致。
- [ ] 加入/取消询价状态与清单数量一致。
- [ ] 加载、空、错误状态可区分。
- [ ] 键盘可操作，移动端筛选入口可用。

## 4.3 分类总览与分类详情（P0）

### 分类总览

- 展示允许公开的分类卡片、分类名称、图片（若有）、说明和产品数量（仅在计数准确时显示）。
- 分类名称和层级来自真实分类数据。
- 无图分类使用统一占位视觉。
- 不将没有产品或未启用的分类作为可进入的空入口，除非产品策略明确允许。

### 分类详情

- 展示分类标题、说明、子分类（如有）和对应产品列表。
- 面包屑反映真实层级。
- 子分类与产品筛选逻辑必须一致。
- 是否包含子孙分类产品要遵循当前 API 语义并在 UI 中保持一致。

### 验收标准

- [ ] 父子分类与后台数据一致。
- [ ] 面包屑层级正确，点击后可返回对应层级。
- [ ] 分类产品数量与 API 统计口径一致。
- [ ] 不存在循环导航或无效分类链接。

## 4.4 产品详情 Product Detail（P0）

### 页面结构

- Breadcrumb。
- 图片图库（主图、缩略图、放大/查看方式沿用现有组件能力）。
- 产品名称、SKU、公开状态、简短说明。
- 规格、材质、尺寸、包装等真实可用字段，单位明确。
- 标签（仅展示已启用且允许公开的标签）。
- 数量输入（如询价需要数量）。
- Add to Inquiry 与 WhatsApp CTA。
- 相关产品（有可靠关联规则时才显示）。

### 调整要求

- 图片切换需更新主图并提供可见选中状态。
- 缺失字段不渲染空标签、空表格行或 `undefined`。
- 不显示内部报价或仅供内部使用的字段。
- 询价消息使用稳定 SKU、当前产品 URL 和用户输入数量。
- 已发布 slug 变化必须提示旧链接影响；重定向属于单独决策，不在前端自行实现猜测逻辑。

### 验收标准

- [ ] 图片切换、缩略图和 fallback 正常。
- [ ] 规格/包装字段按真实数据展示并标明单位。
- [ ] Add to Inquiry 后数量与清单同步。
- [ ] WhatsApp 消息含产品名称、SKU、链接和数量。
- [ ] 未发布/停产状态遵循已定义业务规则。
- [ ] 公共响应不泄露内部报价。

## 4.5 询价清单 Inquiry（P0）

### 主要功能

- 展示已选产品、缩略图、SKU、名称、数量和删除操作。
- 可修改数量、移除单项、清空清单。
- 可填写可选备注，例如定制、包装、目标市场等（若业务确认需要）。
- 生成 WhatsApp 批量消息。
- 清单为空时显示浏览产品入口，并禁用/隐藏无效提交操作。

### 状态一致性规则

- 所有组件共享单一清单状态源，不允许顶部计数、产品复选框、底部浮动栏和询价页面分别维护互不一致的状态。
- 同一产品重复添加时按稳定产品 ID/SKU 合并；数量如何累加必须统一定义。
- 删除、清空、返回、切换语言、分页和刷新时，清单行为应符合项目选定的持久化策略。
- 若使用浏览器存储，必须处理过期产品、数据格式变化和隐私要求；不能把浏览器清单当作服务器正式询盘记录。
- 如业务要求保存正式询盘，必须另行实现有授权/校验/审计的后端持久化流程。
- 点击 WhatsApp 只代表打开链接，不代表消息已发送。

### WhatsApp 消息格式建议

```text
Hello! I'm interested in your products and would like to request a quotation.

1. Product: [Product Name]
   SKU: [SKU]
   Quantity: [Quantity]
   Link: [Product URL]

Could you please share your MOQ, customization options,
packaging details and lead time?

Thank you!
```

### 验收标准

- [ ] 空清单有清晰提示。
- [ ] 重复添加按统一规则合并。
- [ ] 数量只能为有效正数，并有业务上限/输入校验。
- [ ] 单项删除、清空、数量修改后所有计数同步。
- [ ] 生成消息时所有产品均包含正确的 SKU、链接和数量。
- [ ] 消息过长时提示拆分，不静默丢弃产品。
- [ ] WhatsApp 号码来自已验证配置，并正确编码消息参数。
- [ ] 浏览器没有安装 WhatsApp 时可打开网页版本。
- [ ] 埋点不把“打开 WhatsApp”记录为“发送成功”。

## 4.6 Our Factory（P1）

建议内容：

- 设计、生产、质检、包装步骤说明。

建议展示：

规则：

## 4.8 About Us、Contact、FAQ、Privacy、404（P1/P2）

- About Us：品牌故事、团队/历程等真实内容。
- Contact：经核验的 WhatsApp、邮箱、地址和社交链接；联系方式从统一配置读取。

## 6. 国际化（i18n）执行要求

- `zh-CN`、`en-US` 是同一套业务页面的不同语言，不另造独立路由体系。
- 固定 UI 文案使用项目现有 i18n 资源；产品/分类/工厂内容使用现有内容翻译策略。
- 页面标题、导航、面包屑、表单标签、错误提示、按钮、空状态和通知均遵循当前路由 locale。
- 产品 ID、SKU、分类 ID、状态 code 不随语言变化。
- 不使用中文显示名称作为关联键。
- 数量复数、日期/数字格式按 locale 处理。
- 缺失翻译要能被检测；不能长期静默回退为另一种语言。
- 切换语言时清单和当前页面上下文应按产品策略保留。

验收：

- [ ] 所有 P0 页面分别测试 `zh-CN`、`en-US`。
- [ ] 深层 URL 刷新后语言不变。
- [ ] 面包屑、导航和页面标题语言一致。
- [ ] 搜索、空状态、错误提示和按钮无混杂语言。
- [ ] 语言切换后链接有效，不丢失不应丢失的询价状态。

## 7. 技术实现方案（按现有仓库适配）

### 7.1 逻辑职责

| 层 | 责任 | 实施约束 |
|---|---|---|
| UI | 页面、卡片、图库、询价交互、媒体展示 | 优先复用现有组件 |
| API/Route | 查询、输入校验、权限、统一错误 | 复用现有路由与 schema |
| Service | 询价消息构建、产品规则、内容可见性、审计 | 业务规则集中维护 |
| Persistence | 产品/分类/内容/询盘关联 | 以现有 Prisma Schema 为准 |
| Storage | 图片、视频、证书文件 | 复用当前存储服务 |
| i18n | UI 与内容双语 | 复用现有 locale 机制 |
| Analytics | 页面访问、产品查看、WhatsApp 点击 | 口径明确，不虚报发送结果 |

这些是职责边界，不是要求新建同名目录或文件。

### 7.2 API 原则

- 优先复用现有产品、分类、内容和配置 API。
- 不为页面重设计而重复创建数据模型。
- 公开 API 只返回前台必要字段，禁止内部报价、密码、token、私密设置。
- 所有输入经过现有 schema/验证层；前端校验不能替代服务端校验。
- 内容只返回允许公开、已启用的记录。
- 对可能变化的 API 响应先检查真实 schema，不在前端猜字段。
- 统一 loading、empty、error、unauthorized 和 not-found 的处理。

### 7.3 WhatsApp URL 构建

- 号码使用经验证的官方配置，去除号码格式中不允许的字符并验证国家区号规则。
- 消息使用标准 URL 编码，避免空格、换行和特殊字符破坏链接。
- 单品与批量消息共用同一消息构建逻辑，避免两套格式逐渐不一致。
- 产品 URL 应使用当前公开 locale 路由和 canonical 产品路径。
- 对消息长度设定合理阈值；达到阈值提示拆分，不静默截断。
- 统计事件只命名为 `whatsapp_click` 或项目已有等价事件，不命名为 `inquiry_sent`，除非有可信的发送确认机制。

### 7.4 媒体性能

- 图片优先使用现有图片优化能力、响应式尺寸和懒加载。
- 首屏主图避免因错误懒加载造成明显空白；首屏外媒体可懒加载。
- 视频默认封面，用户交互后再加载播放。
- 给图片设置宽高或比例，降低布局跳动。
- 图片/视频加载失败有 fallback。
- 不在本任务中擅自更换 CDN 或存储供应商。

### 7.5 SEO 与分享信息

- 每个公开页面使用唯一、准确的 title/description。
- 产品详情使用规范 canonical URL；中英文页面按现有 SEO/i18n 方案配置语言关联。
- 社交分享图只使用已授权真实素材。
- 404 页面返回正确的未找到语义；草稿或未发布产品不得通过公开 API 泄漏。
- SEO 改造复用项目现有框架能力，不引入重复插件。

## 12. 最终交付定义

本项目的前台改造只有在以下内容都完成后才能标记为交付：

1. 页面和路由调整完成，且没有破坏现有业务能力。
2. 产品、分类、内容和配置使用真实数据。
3. WhatsApp 单品/批量询盘主流程正确。
4. 中英文、响应式、无障碍与错误状态完成回归。
5. 公开 API 和页面没有泄漏内部报价或敏感设置。
6. 后台内容、权限、文件存储和审计继续沿用既有安全边界。
7. 测试报告列明实际运行结果、未完成项和风险。
8. 文档中的建议与最终实际实现差异已更新。

**结论：** 先审计，再建立视觉基线；优先完成首页、产品目录、产品详情和询价闭环（P0）；随后上线工厂与品质内容（P1）；最后完成辅助页面、SEO、无障碍和发布质量（P2）。以真实数据、完整用户流程和可复现测试作为验收依据，而不是只以截图或视觉效果作为完成标准。
