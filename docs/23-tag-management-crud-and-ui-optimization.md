# 商品目录：标签管理 CRUD、展示与数据安全改造方案

- 文档编号：ADM-TAG-CRUD-01
- 版本：1.0
- 状态：已实施（阶段 A–D 已完成，见 `docs/15-implementation-status.md` §15；遗留项见该节 15.6）
- 适用模块：后台 `/tags`、产品标签关联、前台商品卡片标签展示
- 语言要求：后台 `zh-CN` / `en-US`；公开前台默认英文

> 本文是设计与实施基线，不代表代码已经修改。实现前必须核查当前 API、权限编码、Prisma 迁移和真实标签关联数据，不得照抄示例端点后直接覆盖已有接口。

## 1. 背景与当前问题

根据当前截图，标签列表包括 `code`、`Label`、商品数和操作，只有删除按钮；新建 Drawer 中出现“字典项 code”文案，只有英文标签、一个自由文本“类型”字段和启用复选框。现状存在以下问题：

1. **缺少编辑入口**：创建后无法维护标签的英文名、中文名、颜色/样式或启用状态。
2. **文案复用错误**：标签管理表单出现“字典项 code”，应修正为“标签编码”。
3. **类型字段未建模**：当前 Prisma `Tag` 模型没有 `type` 字段，若 UI 提交该值，可能出现未保存或被忽略的假功能。不能继续使用没有业务定义的自由文本类型。
4. **仅展示英文标签**：前台虽然主要使用英文，但后台需要能维护中文标签名，并按 locale 模型支持将来的新语言。
5. **删除风险不明确**：标签可关联多个商品。删除被引用的标签可能同时删除 `ProductTag` 关联，造成商品标签丢失。
6. **列表缺少管理能力**：缺少搜索、状态/使用情况筛选、清晰的启用状态与引用情况，以及对使用中标签的保护提示。
7. **标签语义需要统一**：`featured`、`new-arrival` 可能与商品上的 `isFeatured`、`isNew` 重复表达。开发前需检查实际使用场景，不能直接删除、合并或让两套来源同时驱动同一个展示行为。

## 2. 改造目标与范围

### 2.1 目标

- 标签支持创建、查询、编辑、启用/停用和受保护删除。
- 通过稳定的 `code` 关联商品，展示名称通过翻译数据返回。
- 标签列表一眼能看出编码、中文/英文名称、样式、引用商品数与状态。
- 对正在使用的标签提供安全的停用路径，禁止静默级联删除关联。
- 所有管理文案使用统一 i18n，前台标签按 `en-US` 取名。
- 页面适配桌面、平板与手机，符合项目统一设计 Token。

### 2.2 不在本次默认范围内

- 不构建复杂标签层级树。
- 不默认给标签添加任意 CSS、脚本或富文本样式。
- 不将标签名称当作业务判断条件。
- 不自动把所有现有 `featured` / `new-arrival` 标签迁移到商品布尔字段；需先完成使用情况审计和业务确认。

## 3. 当前数据模型审计结论与约束

当前基线 `database/prisma/schema.prisma` 已有：

- `Tag`: `id`、唯一 `code`、`colorToken`、`enabled`、`translations`、`products`。
- `TagTranslation`: `tagId`、`locale`、`label`，联合主键 `[tagId, locale]`。
- `ProductTag`: `[productId, tagId]` 联合主键，分别引用商品和标签。

因此第一阶段应复用这三张模型，不要另建一套 `TagType` / `ProductLabel` 重复结构。`TagTranslation` 已经可按 locale 扩展，不要把 `zh-CN`、`en-US` 两个固定列直接加到 `Tag` 主表。

### 3.1 建议字段语义

| 字段 | 用途 | 规则 |
|---|---|---|
| `id` | 内部主键 | UUID，不作为 UI 业务编码显示 |
| `code` | 稳定业务键 | 小写 kebab-case 或现有项目统一规范；唯一；创建后原则上不可直接改 |
| `colorToken` | 标签视觉样式 | 只允许项目定义的安全 Token，例如 `tag.success`、`tag.info`、`tag.warning`；不接收任意 CSS |
| `enabled` | 是否可被新商品选择、是否在前台展示 | 停用标签不应自动清除历史商品关联；公共查询只返回启用标签 |
| `TagTranslation.locale` | 语言代码 | 采用规范 locale，如 `en-US`、`zh-CN`，大小写按项目约定统一 |
| `TagTranslation.label` | 该语言下的展示名称 | 英文为公开前台必需；中文供后台使用；后续语言按同一模型扩展 |
| `ProductTag` | 商品与标签关联 | 唯一约束防止重复关联；删除标签前必须检查引用数 |

### 3.2 “类型”字段的处理决策

当前 Prisma `Tag` 没有 `type` 字段，因此**MVP 应移除现有自由文本“类型”输入**，以免 UI 暗示可以保存一个实际上不会持久化的属性。若业务确实需要按用途分组（例如营销标签、供货能力、商品属性），需另立需求，将其设计为 `groupCode` / 字典关联，定义筛选和前台含义后再单独迁移；不能直接把任意字符串写入未建模字段。

## 4. 页面布局与视觉规范

### 4.1 列表页布局

页面顺序：

1. Breadcrumb：`商品目录 / 标签管理`。
2. 页面标题和说明：`标签管理` / `维护商品卡片和详情页展示的标签`。
3. 工具栏：关键词搜索、状态筛选、使用情况筛选、`新建标签` 主按钮。
4. 标签列表表格。
5. 统一分页器：总数、每页条数、页码。

推荐列：

| 列 | 说明 |
|---|---|
| 标签 | 展示实际标签徽标预览，而非只显示纯文本 |
| 编码 | `code`，使用等宽字体，可复制；默认不可普通编辑 |
| 名称 | 英文名称作为主文本，中文名作为次文本；若当前管理语言为英文则反向排列也可以，但规则要统一 |
| 样式 | 颜色 Token 的小预览和 Token 名称 |
| 商品数 | 当前关联的商品数量，可点击进入使用商品列表或打开 Drawer 查看使用情况 |
| 状态 | 启用/停用，使用文字 + 状态样式，不只依赖颜色 |
| 更新时间 | 如项目审计字段存在则展示；不存在时可暂不添加，不为展示而伪造数据 |
| 操作 | 编辑、启用/停用、删除（仅在满足删除条件时启用） |

建议在列表上方提供：

- 搜索：按 `code`、所有已配置语言的 `label` 模糊搜索；服务端分页时由 API 执行。
- 状态：全部 / 启用 / 停用。
- 使用情况：全部 / 已使用 / 未使用。
- `清除筛选`。
- `新建标签`。

默认按 `code` 升序或 `updatedAt desc` 稳定排序；选一种并保持跨页面一致。分页大小限制由 API 白名单控制。

### 4.2 标签预览

标签在列表和表单中应使用同一个 `TagBadge` 组件，避免后台预览与前台样式不一致。组件仅接收 `label` 和允许的 `colorToken`，不接受数据库值直接拼接到 `style`、className 或 CSS 字符串。

### 4.3 新建/编辑 Drawer

新建和编辑必须复用一个 `TagFormDrawer`。桌面端建议宽度 560–640px；手机端全屏或接近全屏。字段安排：

**基础信息**
- 标签编码 `code`（必填；编辑时只读或明确提示变更会影响引用，默认不允许更改）。
- 英文标签名 `en-US`（必填，前台展示）。
- 中文标签名 `zh-CN`（可选；若后台中英文都作为强制运营要求，可配置为必填，但需迁移存量数据）。
- 标签样式 `colorToken`（预设 Token 下拉框，并即时预览）。
- 启用状态 `enabled`（新建默认启用；编辑时可切换，或统一通过列表状态操作）。

**不显示**
- 不把商品数做成可编辑表单字段。
- MVP 不保留未持久化的自由文本 `类型`。
- 不提供任意 CSS 颜色/样式文本输入。

表单交互：
- 创建/编辑标题明确区分。
- 必填项显示校验消息，标签直接关联到输入框。
- 保存期间禁用重复提交并显示 loading。
- 保存成功关闭 Drawer、刷新当前查询结果并 Toast 成功提示。
- 保存失败保留用户输入并显示字段错误/全局错误。
- 关闭时若存在未保存修改，弹出离开确认。
- 支持 Escape 关闭、焦点管理和键盘操作。

### 4.4 删除确认交互

- 删除操作打开确认弹窗，展示标签编码、名称和关联商品数。
- 若关联商品数大于 0，禁用物理删除按钮，并解释“此标签正在被 N 个商品使用，请先停用标签；如需移除关联，请到商品管理中处理”。
- 服务端是最终判断依据；即使前端显示数为 0，也必须由删除 API 在事务/约束保护下重新检查。
- 标签停用后保留历史关联；前台隐藏该标签，但后台商品编辑页可提示该关联已停用，允许有权限用户显式移除或更换。
- 若标签未被引用，允许删除，并要求 `tags.delete`（实际权限编码需核查）。

## 5. 国际化规则

- 后台 UI 文案统一通过 `zh-CN` / `en-US` 资源管理，不散落硬编码。
- 公开前台使用英文标签：`label(locale='en-US')`；若英文翻译缺失，开发/测试环境显示明显数据质量告警，生产环境可暂时回退到 `code`，但不能回退到中文作为英文页面主文案。
- 后台在当前 locale 优先展示该语言标签；若缺失，可以回退到 `en-US` 并用提示标明翻译缺失。
- locale 规范和回退顺序应使用项目已有的 i18n 工具，不另建独立规则。
- 新增未来语言仅需要添加 `TagTranslation` 记录和对应后台翻译资源，不需要修改数据库列。

## 6. API 契约建议

以下路径是建议契约，实施前应适配当前 NestJS Controller 路由和统一响应结构，避免重复端点。

### 6.1 列表

`GET /api/admin/tags?q=&enabled=&usage=&page=1&pageSize=20&locale=zh-CN`

响应至少包含：

```json
{
  "items": [
    {
      "id": "uuid",
      "code": "oem",
      "colorToken": "tag.info",
      "enabled": true,
      "translations": {
        "en-US": "OEM available",
        "zh-CN": "支持 OEM"
      },
      "productCount": 0
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

列表返回 `productCount` 聚合值，避免前端对每个标签逐一请求商品数造成 N+1 查询。`translations` 为当前已存翻译的映射，不应假定每种语言都存在。

### 6.2 创建

`POST /api/admin/tags`

```json
{
  "code": "oem",
  "colorToken": "tag.info",
  "enabled": true,
  "translations": [
    { "locale": "en-US", "label": "OEM available" },
    { "locale": "zh-CN", "label": "支持 OEM" }
  ]
}
```

服务端必须：
- 校验 `code` 格式和唯一性；处理并发唯一冲突并返回稳定错误码。
- 校验翻译 locale、长度、重复 locale 和必需英文名称。
- `colorToken` 必须存在于允许清单。
- 不接受客户端指定的 `id`、商品关联列表、`productCount`、系统保护属性等字段。
- 验证操作者有创建权限并记录审计事件。

### 6.3 详情与更新

- `GET /api/admin/tags/:id`
- `PATCH /api/admin/tags/:id`

建议更新 DTO：

```json
{
  "colorToken": "tag.success",
  "enabled": true,
  "translations": [
    { "locale": "en-US", "label": "OEM available" },
    { "locale": "zh-CN", "label": "支持 OEM" }
  ],
  "version": 3
}
```

`code` 在编辑更新中默认不可变。若业务明确要求改码，必须提供单独的迁移流程，校验所有引用并更新缓存/外部引用，不允许普通表单直接变更。若项目已有 `updatedAt` 或 `version`，使用已有并发控制；没有时可先采用更新时间/版本字段策略评估，不要无理由加字段。

标签与翻译写入应使用事务，避免主表保存成功但某个语言翻译失败。

### 6.4 启用/停用

`PATCH /api/admin/tags/:id/status`

```json
{ "enabled": false }
```

状态端点可以统一为编辑接口的一部分，但需避免一键操作绕过更高的权限要求。操作后应使后台标签列表、商品编辑表单选项和公开商品标签缓存失效。

### 6.5 删除

`DELETE /api/admin/tags/:id`

服务端流程必须重新查询标签和关联商品数：

1. 检查 `tags.delete` 权限（或实际项目定义的权限码）。
2. 检查标签存在。
3. 若 `ProductTag` 关联数 > 0，返回 `TAG_IN_USE` / HTTP 409，不删除关联。
4. 若未被引用，在事务/外键约束保护下删除翻译和标签；删除翻译是否由 FK cascade 处理需根据当前 schema 与数据库确认。
5. 写审计事件，失效缓存。

不得让标签删除自动级联清空商品关联。当前基线中 `ProductTag.tag` 使用 `onDelete: Cascade`，这是需要特别审查的风险点。建议应用服务先严格阻止删除被引用的标签；进一步建议把 `ProductTag.tag` 外键改为 `Restrict`/数据库等效约束作为第二道保护，并通过版本化迁移实现。在确认当前数据库支持和迁移策略前，不可直接修改生产约束。

## 7. 权限与审计

建议权限粒度（最终名称必须从 `Permission` 中核实）：

- `tag.read`：查看列表/详情。
- `tag.create`：新建标签。
- `tag.update`：编辑标签名称、样式。
- `tag.status.update`：启用/停用；如果现有权限体系不需要这么细，可与 update 合并。
- `tag.delete`：删除未被引用的标签。

服务端每个端点必须单独鉴权；隐藏按钮只用于改善体验，不构成安全控制。

审计记录至少包含操作者、时间、操作类型、标签 ID/code、变更前后差异。只记录标签元数据，不记录 session/token 等秘密信息。对翻译变更建议按 locale 记录差异。

## 8. 商品编辑页与前台展示联动

### 8.1 后台商品编辑

- 标签选择器调用统一的标签选项 API，默认仅返回 `enabled=true` 标签。
- 已有商品若关联了停用标签，编辑页面仍需显示该历史关联，并标明“已停用”；用户保存其他商品字段时不可静默把该关联删除。
- 新增标签后，商品编辑页面在刷新/重新打开后即可选择；若采用 React Query/SWR 等查询缓存，应在创建/编辑/启停/删除后使相关 query key 失效。

### 8.2 前台商品卡片和详情

- 只显示 `enabled=true` 的标签，并按当前公开 locale（默认 `en-US`）取翻译。
- 标签名称使用统一 `TagBadge` 组件；标签排序规则要确定（建议按标签配置顺序或产品关联顺序），不能依赖数据库自然顺序。
- 前台公共 DTO 只含必要字段：`code`（确有需要时）、`label`、`colorToken`；不返回内部管理字段和产品内部价格。
- 不允许数据库里的 `colorToken` 被直接解释为 CSS；映射到 UI 允许的 Token。
- 需测试标签停用之后，商品卡片、详情页、搜索结果、SSR/ISR 缓存均不再向访客展示该标签。

### 8.3 `featured` / `new-arrival` 与商品布尔字段的去重

项目模型同时有 `Product.isFeatured` / `Product.isNew` 和自由标签体系。实现前检查：

1. 首页精选/新品区是否由布尔字段驱动。
2. 商品卡片角标是否从 `ProductTag` 驱动。
3. `featured` / `new-arrival` 标签当前的商品关联是否与两个布尔字段一致。

建议把职责明确为：布尔字段负责首页精选/新品分区；标签负责可配置的通用徽标。若前台只需要一种“Featured/New”徽标，则应选择单一事实来源并制定数据迁移，不要让两套机制显示双重徽标或产生冲突。任何合并前先产出差异清单，不能直接物理删除现有标签。

## 9. 数据与迁移计划

### 阶段 A：只读审计

- 核实数据库 Provider、当前 schema migration 和表实际 FK。
- 统计标签数量、每个标签的商品关联数、翻译 locale 覆盖率、重复/无英文翻译项。
- 核对现有 API 的字段名与权限码。
- 对 `featured` / `new-arrival` 生成与 `isFeatured` / `isNew` 的差异报表。

### 阶段 B：前后端兼容改造

- 修正“字典项 code”等错误文案。
- 建立共享 `TagFormDrawer`、搜索过滤与启停操作。
- 补齐创建/详情/更新/状态 API；如果已有接口则扩展而非重建。
- 不需要 schema 更改时，不创建空迁移。

### 阶段 C：数据约束加固（经评审后）

- 评估 `ProductTag.tag` 外键从 Cascade 改成 Restrict 的数据库迁移。
- 如需要，增加审计/并发字段或标签组字段，必须先说明用途、回填和回滚；当前 MVP 不新增无业务用途的 `type` 字段。
- 将数据清洗和翻译回填与功能发布拆开，保证可观察、可回滚。

### 阶段 D：验证与发布

- 测试环境运行迁移和全量用例。
- 发布时先上线后端兼容 API，再发布前端。
- 检查日志、错误率、标签查询/保存延迟和关联数据未减少。
- 回滚优先回退前端与应用版本；约束迁移按已演练的反向迁移/前向修复方案处理，禁止盲目 drop constraint。

## 10. 前端组件和代码组织建议

按现有目录和代码模式落地，不要凭文档新建重复的 API client 或 UI 库。可参考以下职责拆分：

```text
apps/admin/src/features/tags/
├── api.ts                 # list/create/detail/update/status/delete API
├── hooks.ts               # query/mutation/cache invalidation
├── types.ts               # DTO / query params
├── tag-list-page.tsx      # 页面组合
```

## 11. 错误处理与用户反馈

| 场景 | 预期行为 |
|---|---|
| code 重复 | 字段级错误“此编码已存在”，保留已填内容 |
| 英文名称为空 | 阻止保存并定位字段 |
| 未知颜色 Token | 服务端校验拒绝，前端只显示允许项 |
| 没有权限 | 按权限隐藏操作，同时 API 返回 403 |
| 删除时标签已被新商品引用 | API 返回 409 `TAG_IN_USE`，显示最新商品数并引导停用 |
| 标签详情/编辑加载失败 | 显示重试入口，不显示空白 Drawer |
| 保存时网络中断 | 保留输入，防止重复提交；重试前处理幂等/唯一冲突 |
| 并发编辑 | 检测版本冲突并提示刷新后重试，不静默覆盖别人修改 |
| 停用标签仍被历史商品引用 | 保留关系，在后台展示停用状态；公开端隐藏标签 |
| 翻译缺失 | 标出缺少语言，不把错误翻译写入其他 locale |

## 12. 测试与验收标准

### 12.1 功能测试

1. 标签列表加载成功，列出 code、双语名称、样式、商品数和状态。
2. 搜索 code、英文标签和中文标签均命中正确记录。
3. 状态筛选、已使用/未使用筛选和分页组合正确。
4. 新建合法标签成功，刷新后仍存在，商品编辑页能选择。
5. 重复 code 被前后端拒绝。
6. 新建时保存 `en-US`、`zh-CN` 翻译；编辑其中一种语言不会覆盖另一种语言。
7. 编辑标签名称/颜色成功，列表和前台展示更新。
8. 未使用标签可删除；确认弹窗显示标签名称和编码。
9. 有商品关联时删除被前端提示，并由后端以 409 拒绝；`ProductTag` 记录必须保持不变。
10. 停用标签后不能被新关联选择，历史关联保留，公共商品页面不显示停用徽标。
11. 标签保存后缓存及时刷新，不能出现长时间旧标签。
12. 修改 `featured` / `new-arrival` 前先跑差异测试，首页精选/新品与卡片徽标不出现双重或漏显示。

### 12.2 安全测试

- 未登录请求全部管理 API 均被拒绝。
- 无 `tag.create/update/delete` 权限的用户不能通过直接请求绕过 UI。
- 不允许通过 DTO 注入 `productCount`、商品关联、ID、未知字段或未知颜色 token。
- 删除时并发创建 `ProductTag` 仍不能导致已引用标签被删：依赖事务、合适锁/隔离和数据库 FK 约束兜底。
- 搜索参数使用 ORM 参数化查询；分页大小限制；不得把标签 label 当 HTML 渲染。

### 12.3 响应式和可访问性

- 360px 手机：表格改为卡片或横向滚动容器，操作可访问；Drawer 全屏。
- 平板：过滤器可换行，表格不遮挡操作列。
- 桌面：列表密度清晰，工具栏在首屏可见。
- 所有字段有 Label，弹窗键盘可操作、焦点可见、关闭后焦点返回触发按钮。
- loading、空数据、API 错误、无权限都有明确状态。

### 12.4 Definition of Done

- lint、typecheck、相关单元/集成测试、build 通过；未能执行的检查必须说明原因。
- 前端新增/编辑/删除/启停均有真实 API 功能，不留占位按钮。
- 使用中标签删除保护已由服务端测试覆盖。
- i18n 中英资源完整；公共前台展示默认英文。
- 有 schema 变更时提供版本化 migration、数据核查、回滚流程；无 schema 变更时不生成空 migration。
- 更新 API 类型、测试、审计行为和相关文档。

## 15. 业务决策清单

实施前确认以下事项；未确认时采用本文默认值：

1. **中文标签名是否必填**：默认可选，英文必填，因为公开前台默认英文。
2. **标签类型**：默认移除未建模的自由文本字段；未来如需分类，先定义 `groupCode`/字典类型。
3. **使用中标签删除**：默认禁止物理删除，提示停用；先在商品中移除全部引用后才允许删除。
4. **编码是否可修改**：默认不可修改，避免影响业务引用。
5. **样式选项**：默认只能选项目定义的 `colorToken`，不允许自由填写 CSS。
6. **featured/new-arrival**：默认不自动迁移，先审计布尔字段与标签关联的差异，确保只保留一套负责同一显示行为的事实来源。
