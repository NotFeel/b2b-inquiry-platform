# B2B Inquiry Platform：后台商品管理页面优化与技术实施方案

> 文档状态：可执行设计方案，待代码审计与评审后实施。依据用户提供的三张后台截图及项目基线文档。截图能确认可见
> UI 症状，但不能证明实际
> schema、API、权限码或代码实现。本文件不代表代码已修改或测试已通过。

## 1. 目标与决策摘要

### 1.1 本次明确需求

1.  「商品目录 → 商品管理」列表增加价格展示。
2.  新建/编辑商品页「状态与展示」移除「新品标记、精选标记、预售（前台首页）」三个复选框。
3.  新品、精选、预售等运营属性统一在「标签与运营」中维护。
4.  价格是后台内部运营/报价信息，不得因此暴露到前台页面或公开 API。
5.  发布状态与生命周期保持独立，不能把「预售」标签自动等同于生命周期状态。

### 1.2 推荐决策

  --------------------------------------------------------------------------------------------------
  项目                                推荐决策
  ----------------------------------- --------------------------------------------------------------
  列表价格列                          显示真实价格及币种；无价格显示「未设置」，不能伪造 0

  价格来源                            优先复用已有商品参考价或报价模型；先查
                                      schema/API，不重复建字段

  价格字段不存在                      先确认价格含义、币种、精度和多报价规则，再评审最小迁移

  新品/精选/预售                      以结构化标签关系作为唯一运营入口

  标签关联                            使用稳定 ID/code；标签名称用于展示，支持中英文

  数据兼容                            先盘点旧字段与消费者，再做映射、回填和对账；不直接删除旧字段

  前台安全                            价格仅由授权后台 API 返回，公开 API 使用字段白名单
  --------------------------------------------------------------------------------------------------

## 2. 截图审查与当前可见问题

### 2.1 商品管理列表

截图中的列包含主图、SKU、名称、所属品类、发布状态、生命周期、状态、图片数、更新时间和操作，当前未见价格列。建议在
SKU/名称之后或所属品类之前增加「价格」列；金额与币种格式全站统一，如
`USD 12.50`。空值显示「未设置」，不要显示为
`0.00`。若存在多币种或多层级报价，按已确认的默认参考价规则显示，或显示「多种报价/查看报价」，不能随机选取一条。排序必须由服务端实现，不要只对当前页做前端排序。

### 2.2 新建/编辑商品

「状态与展示」目前包含发布状态、生命周期、排序值，以及新品、精选、预售复选框；「标签与运营」已经有
`featured`、`new-arrival`、`oem`、`preorder`
等标签。这会造成同一业务含义有两个入口、数据可能不一致。

调整后： -
删除「状态与展示」中的三个运营复选框和仅用于解释它们的提示。 -
保留发布状态、生命周期、排序值。 -
在「标签与运营」中保留标签多选，作为新品/精选/预售的唯一维护入口。 -
新增和编辑共用字段分组、校验和标签选择器。 -
页面仍沿用项目当前路由/页面模式，不要求为了本次改造强制换成弹窗或抽屉。

建议表单分组顺序：基本信息 → 发布与排序 → 商品规格 → 箱规规格 →
标签与运营 → 图片图库 → SEO → 底部操作区。

## 3. 价格字段：先确认业务含义

开发前必须检查 schema、迁移、商品服务、报价模型、后台列表 API、公开产品
API 和测试，确认： - 是否已有
`price`、`referencePrice`、报价表或关联模型； -
价格究竟是内部参考价、零售价、成本价、批发价还是客户报价； -
是否需要币种、默认币种、多币种、数量阶梯价或有效期； -
哪些后台角色可以查看价格； - 后台与前台是否共用 DTO/API。

### 3.1 最小实施路径

**A. 已有唯一参考价：**
扩展后台列表响应并增加价格列，不新增迁移。若本次只要求列表展示，不擅自扩大成新增价格编辑需求。

**B. 已有报价关联模型：** 明确默认显示哪一种报价；在 Service
层聚合，避免 N+1 查询。多报价不能用随机值代替。

**C. 没有可用价格：** 先确认业务定义与币种规则，再评审
schema/迁移、API、权限、审计和测试。金额应使用精确数值类型而非浮点数；具体精度遵循项目规范。不得用
mock/固定值填充。

### 3.2 列表显示规则

  数据状态        展示                         说明
  --------------- ---------------------------- ----------------------------
  有金额和币种    `USD 12.50` 或统一货币格式   全站一致
  金额为空        `未设置`                     不显示成 0
  多币种/多报价   `多种报价` 或查看入口        仅当模型真实支持
  无查看权限      `—` 或不返回字段             服务端执行权限控制
  接口错误        明确错误状态                 不以旧缓存/mock 冒充真实值

### 3.3 安全边界

-   查看价格必须由后端认证与权限规则控制；先核对权限命名约定，不臆造权限码。
-   公开产品列表、详情、SEO 结构化数据、页面
    HTML、客户端状态和公开缓存不得带出内部价格。
-   不能只靠前端隐藏列保护价格。
-   若前后台共用 DTO，拆分后台管理 DTO 与公开
    DTO，或通过严格字段白名单隔离。

## 4. 新品、精选、预售统一到标签

### 4.1 建议标签 code

  --------------------------------------------------------------------------------------
  用途           建议 code       中文           英文           注意
  -------------- --------------- -------------- -------------- -------------------------
  新品           `new-arrival`   新品           New Arrival    逻辑按 code
                                                               判断，不按显示名

  精选           `featured`      精选           Featured       核对首页/精选区消费规则

  预售展示       `preorder`      预售           Pre-order      不自动等同生命周期
                                                               `preorder`

  OEM 能力       `oem`           支持 OEM       OEM Available  能力标签而非状态
  --------------------------------------------------------------------------------------

以上为建议映射。先检查数据库现有
code、重复项、关联数量与前台消费方式；优先复用已有稳定
code，不为匹配示例而重命名正在使用的 code。

### 4.2 单一事实来源

-   新品、精选、预售运营展示统一从商品标签关系读取。
-   表单加载从服务端回显标签；提交标签 ID/code
    数组；后端校验标签存在、启用且可分配。
-   不允许标签关系与独立布尔值成为两个可写数据源而没有同步规则。
-   若性能需要冗余字段，必须定义唯一写入路径、同步机制与一致性测试。
-   标签加载失败要显示错误/重试，不能让用户误以为已保存。

### 4.3 生命周期边界

项目基线将发布状态与生命周期分开：发布状态例如
`draft / published / unpublished`；生命周期例如
`available / preorder / discontinued`。生命周期 `preorder`
表示业务状态；标签 `preorder`
表示运营展示或营销分类。是否要求二者同时成立属于业务规则，必须明确后在
Service/API 校验，不能仅凭同名自动同步。

## 5. 兼容与数据迁移

**禁止直接删除旧字段。** 先全仓搜索旧复选框绑定字段、API
payload、服务端写入、前台消费和历史数据。

推荐步骤： 1. 盘点旧字段、标签关系和所有读写位置。 2.
确认旧布尔值到稳定标签 code 的映射。 3. 统计旧值为
true、已有标签、两边冲突的商品数。 4.
在备份与可重跑脚本保护下回填，避免重复关联。 5.
对冲突数据单独报告；旧值为 false 但已有标签时，不擅自删除标签。 6.
必要时短期双读对账，但不长期双写。 7.
切换表单、后台展示和前台消费逻辑到统一标签关系。 8.
确认无旧读写、测试通过且回滚方案就绪后，才单独删除旧字段。

迁移脚本应幂等，支持 dry-run，使用稳定
ID/code，输出迁移前后数量、跳过数、冲突数、失败
ID；生产执行前先备份并在测试库验证。

## 6. 技术实施分层

### 6.1 开工前审计

检查
`AGENTS.md`、README、包脚本、商品列表/新建/编辑页、共享表单、标签选择器、schema/迁移、价格/报价模型、后台与公开
API、权限码、审计日志、测试，以及首页新品/精选/预售逻辑和缓存。产出真实文件路径、真实字段/API、复用组件、是否需要迁移、受影响前台逻辑和测试命令清单。

### 6.2 分层职责

-   **UI：**
    价格列、格式化、加载/空/错误状态；移除三个复选框；标签选择器统一维护运营属性。
-   **API/Route：** 后台列表只返回经授权的价格；标签参数用
    ID/code；使用项目现有 schema 校验。
-   **Service：**
    校验标签存在、启用、可分配；事务内保存商品和标签关联；价格查询避免
    N+1；统一旧字段兼容逻辑。
-   **Persistence：** 优先复用现有
    schema；确有缺口才迁移；标签关系有外键/唯一约束；金额使用精确数值与明确币种。
-   **Security/Audit：**
    后端价格权限校验；标签变更按项目审计策略记录；敏感报价不无必要写入日志。

### 6.3 API 兼容

-   后台独立 API 优先扩展后台响应。
-   前后台共用 API/DTO 时先隔离公开字段。
-   旧 payload 的过渡策略按实际消费者决定，不能无评估直接删除字段。
-   如需短期兼容旧布尔值，应由服务端从标签关系派生并设置下线期限；禁止长期双数据源。
-   API、字段和权限码名称以仓库现状为准。

## 7. 页面交互与视觉细节

### 7.1 列表列顺序建议

主图 → SKU → 名称（当前 locale）→ 价格 → 所属品类 → 发布状态 → 生命周期
→ 运营标签/状态 → 图片数 → 更新时间 → 操作。

如宽度不足，允许横向滚动或列配置；不要挤压操作按钮。价格筛选（已设置/未设置）属于可选增强；新品/精选/预售快捷筛选应基于同一标签筛选
API，不再维护独立布尔筛选源。

### 7.2 表单细节

-   「发布与排序」仅保留发布状态、生命周期、排序值。
-   标签多选支持搜索、清晰回显、键盘操作与移除。
-   标签选项使用双语名称；固定 UI 文案进入现有 i18n 资源。
-   下拉菜单应处理
    z-index、滚动容器和焦点，不能被卡片裁剪或被底部操作栏遮挡。
-   保存错误映射到字段或表单顶部；保存成功给出反馈。

## 8. 测试计划与验收标准

### 8.1 价格列

-   有价格时金额/币种正确；空值显示未设置；多报价遵循确认规则。
-   分页、搜索、品类和标签筛选后行与价格正确对应。
-   服务端排序（如实现）跨页正确。
-   无权限用户无法通过 API 读取价格。
-   公开列表/详情 API、HTML、SEO 数据不包含内部价格。
-   接口失败不展示 mock 值或假 0。

### 8.2 标签统一入口

-   新建/编辑选择、保存、回显、移除标签均正确。
-   重复提交不产生重复关联；无效/停用/无权标签由服务端拒绝。
-   旧字段与标签冲突按迁移规则处理。
-   首页/列表新品、精选、预售展示按统一规则变化。
-   生命周期 `preorder` 与标签 `preorder` 分别测试。
-   中文和英文后台标签名称正确。

### 8.3 回归与 Definition of Done

-   新建、编辑、草稿、发布、下架流程正常。
-   品类、SKU、slug、规格、包装、图片上传/删除、SEO 不受影响。
-   角色权限、审计、筛选、分页正常。
-   桌面/平板布局无重叠；标签下拉不被裁剪；键盘焦点可见。
-   无控制台错误、未处理 Promise rejection 或 API schema 错误。
-   已记录真实文件、schema、API、权限；价格来自真实持久化数据；公开 API
    无价格泄漏；三个复选框已移除；标签关系持久化正确；迁移已对账或确认不需要；相关测试已运行并记录结果；中英文、响应式、错误状态通过验收；文档已更新。

## 9. 推荐实施拆分

### Sprint 0：审计与业务确认

确认价格含义、币种、多报价规则和权限；盘点旧字段、标签关系、前台消费者；输出真实代码路径和迁移决策。价格定义未确认前不新增字段。

### Sprint 1：标签入口统一

移除三个复选框；优化标签选择器与双语文案；服务端统一写入标签关系；修正前台展示消费逻辑并测试。

### Sprint 2：后台价格展示

扩展后台列表查询/DTO；增加价格列和格式化；执行权限校验；如模型缺失，先走业务确认和迁移评审；验证公开
API。

### Sprint 3：迁移与回归

如有需要，执行幂等回填并对账；确认安全后清理旧字段/代码；运行相关测试并记录结果。

### Sprint 4：体验收尾

检查表格宽度、响应式、中英文、错误提示、空状态和键盘操作；更新问题清单与技术决策文档。

## 10. 风险与待确认事项

  项目                   处理方式
  ---------------------- --------------------------------------------
  价格字段是否存在       查 schema、报价模型和 API
  价格业务含义与币种     由业务明确，避免参考价/成本价/客户报价混用
  价格权限               后端授权与公开 DTO 白名单
  旧复选框数据源         全仓搜索所有读写与前台消费
  标签 code 是否已存在   复用稳定 code，不按名称重复建标签
  预售标签与生命周期     单独定义业务校验/展示规则
  首页运营逻辑           确认首页当前读取布尔值还是标签
  旧 API 客户端          评估兼容期与下线计划

## 11. 实施时禁止事项

-   不得用假数据、固定金额或 0 占位。
-   不得把内部价格加入公开 API 后仅靠 CSS 隐藏。
-   不得保留两套独立可写的运营状态而没有同步规则。
-   不得把预售标签自动等同于生命周期。
-   不得因 UI 改动直接删字段或历史关联。
-   不得硬编码标签 ID、翻译名称或未经确认的权限码。
-   不得声称测试通过，除非真实运行并记录结果。
