# 系统管理：角色权限 CRUD 与菜单权限配置改造方案

> 文档编号：18  
> 适用模块：后台管理端 / 系统管理 / 角色权限  
> 目标：为角色管理补齐新增、查询、编辑、删除/安全删除能力，并实现可查询、可配置、可保存和可验证的菜单权限。  
> 语言：后台界面支持 `zh-CN` / `en-US`；权限 code、菜单 code 和 API 字段不得依赖展示语言。

---

## 1. 现状问题与改造目标

根据当前 `/zh-CN/roles` 页面截图，页面目前仅展示 `code`、名称、用户管理数、权限数和 `system/custom` 类型，存在以下问题：

1. 页面没有“新建角色”入口，无法创建自定义角色。
2. 表格没有“查看权限 / 编辑 / 删除”等操作，无法维护角色基础信息。
3. 权限数只是一个数字，不可点击、不可解释；无法查看某角色具体有哪些菜单或操作权限。
4. 当前页面没有角色搜索、类型筛选、权限配置入口和完整的保存反馈。
5. 必须明确系统角色与自定义角色的安全边界，避免管理员误修改 `super_admin` 或删除仍被用户使用的角色。
6. 权限 UI 只能是权限管理的入口，不能代替后端授权；绕过界面直接调用 API 时，服务端也必须拒绝无权操作。

### 1.1 目标状态

角色页面应可完成以下闭环：

- 查看、搜索、筛选角色，并查看角色关联用户数和权限数。
- 新建自定义角色，编辑角色名称/描述等基础信息。
- 打开权限配置界面，查询已有菜单与可分配操作权限。
- 通过树形勾选配置权限，保存后重新读取并准确回显。
- 查看自定义角色所关联的用户；删除前明确说明影响。
- 保护系统角色与最后一个有效超级管理员，不允许通过角色编辑绕过权限保护。
- 对角色创建、更新、权限变更、删除/禁用写入审计日志。

## 2. 页面交互设计

### 2.1 页面标题区

页面标题：`角色与权限` / `Roles & Permissions`。

说明文案：
- 中文：`管理后台角色、菜单访问范围与操作权限。系统角色受保护。`
- 英文：`Manage admin roles, menu access and action permissions. System roles are protected.`

操作区：
- 主按钮：`新建角色 / Create role`，需要 `roles.create` 权限。
- 搜索输入：按角色 code、名称或描述搜索，支持 Enter 触发与清除。
- 类型筛选：全部 / 系统角色 / 自定义角色。
- 可选的分页页大小：20、50、100；后端限制最大页大小。

页面布局建议：

```text
角色与权限                                      [新建角色]
管理后台角色、菜单访问范围与操作权限。系统角色受保护。
[搜索角色 code / 名称................] [类型：全部 v] [搜索]
┌────────────┬────────────┬────────┬────────┬────────┬───────────────┐
│ 角色编码   │ 角色名称   │ 类型   │ 用户数 │ 权限数 │ 操作          │
├────────────┼────────────┼────────┼────────┼────────┼───────────────┤
│ super_admin│ 超级管理员 │ 系统   │ 1      │ 52     │ 查看权限      │
│ sales      │ 销售人员   │ 自定义 │ 3      │ 11     │ 权限 / 编辑 / …│
└────────────┴────────────┴────────┴────────┴────────┴───────────────┘
共 N 条                                      每页 20 条   [分页]
```

### 2.2 表格字段与操作

| 字段 | 说明 | 交互约束 |
|---|---|---|
| 角色编码 `code` | 稳定的机器标识，例如 `sales` | 创建后默认不可修改；不随中英文切换改变 |
| 角色名称 | 根据当前 locale 展示的名称 | 不能为空；自定义角色可编辑 |
| 类型 | 系统角色 / 自定义角色 | 来源于 `isSystem`，不是一个可手动编辑的文字字段 |
| 用户数 | 当前关联的后台用户数量 | 可打开用户清单或查看受影响用户 |
| 权限数 | 已授予的唯一 permission 数量 | 可点击“配置权限”查看详情，不只展示数字 |
| 更新时间 | 最近一次修改时间 | 统一显示用户时区；后端储存 UTC |
| 操作 | 查看权限、编辑、删除 | 根据后端授权、系统角色保护、用户关联状态动态启用/禁用 |

建议操作规则：

- 所有角色：可查看基础信息和当前权限（需要相应 read 权限）。
- 自定义角色：满足 `roles.update` 时可编辑；满足 `roles.permissions.update` 时可配置权限。
- 系统角色（`isSystem=true`）：基础信息和权限默认只读，隐藏或禁用编辑/删除，并说明“系统角色受保护”。如未来业务确需编辑某个系统角色，必须设计单独的审批/受控流程，不在本次范围内。
- 删除：仅自定义角色可执行；角色未分配任何用户时才允许。角色有关联用户时，前端提示先将这些用户重新分配角色；后端仍需二次校验。可选未来新增“停用角色”流程，但不要把 `system/custom` 类型错误展示为启用状态。

### 2.3 新建角色弹窗/抽屉

建议使用宽度 520–640px 的右侧 Drawer 或居中 Modal，字段：

| 字段 | 控件 | 规则 |
|---|---|---|
| 角色编码 | Input | 必填；小写字母、数字、下划线；创建后不可修改；唯一 |
| 角色名称（中文） | Input | 必填，长度按后端校验限制 |
| 角色名称（英文） | Input | 推荐必填；至少为 `en-US` 提供稳定显示名 |
| 描述 | Textarea | 选填；说明该角色的业务范围 |
| 初始权限 | 可选的配置步骤 | 建议创建时先保存角色，再进入权限配置；避免新建流程与复杂权限树混在一个超长表单中 |

交互：保存时按钮显示 Loading、防止重复提交；成功后关闭表单、刷新列表并提示成功；失败保留用户输入并显示字段级或顶部错误。

### 2.4 编辑角色

- `code`、`isSystem` 只读；名称和描述可编辑。
- 编辑基础信息与编辑权限分为两个清楚的入口：`编辑信息`、`配置权限`。
- 角色名称需要国际化时优先复用现有翻译/名称模型；当前 schema 中 `Role.nameKey` 是翻译 key，不应直接把中文显示文案覆盖为 `nameKey`。需在实施前确认当前角色名称究竟来自 `nameKey` + i18n 字典，还是实际数据中存放的 key 字符串。
- 如果当前产品要求管理员可维护中英文角色名，建议采用角色多语言表（例如 `RoleTranslation(roleId, locale, name, description?)`）；这属于数据库变更，必须单独迁移，不可将 `nameKey` 同时当作翻译 key 和用户输入的实际名称。

### 2.5 权限配置界面（核心）

从角色列表点击 `配置权限`，打开宽屏 Drawer（建议 760–960px）或独立权限配置页。移动端改为全屏页面。

布局：

```text
配置角色权限 — 销售人员 (sales)                 [取消] [保存权限]
搜索权限 [.............................]   [全部展开] [全部折叠]
已选择 11 项                                  [清空选择]
┌─────────────────────────┬────────────────────────────────────────┐
│ 菜单 / 模块树            │ 权限详情                                │
│                         │                                        │
│ □ 工作台                │ □ 访问工作台                             │
│ □ 商品目录              │ □ 查看商品  □ 新建商品                    │
│   □ 商品管理            │ □ 编辑商品  □ 上下架                      │
│   □ 品类管理            │                                        │
│ □ 询盘与分析            │ □ 查看客户  □ 编辑客户                    │
│   □ WhatsApp 客户       │                                        │
│ □ 报价与文件            │                                        │
│ □ 系统管理              │                                        │
└─────────────────────────┴────────────────────────────────────────┘
```

实现细节：

1. 菜单树由后端返回，不在前端写死菜单名称或权限 code。
2. 菜单展示名称使用 `MenuTranslation` 当前语言；业务判断始终使用 `Menu.code` / `Permission.code`。
3. 菜单节点有 `permissionCode` 时，可把它显示为该菜单的页面访问权限；分组节点 `permissionCode=null` 不应生成不存在的权限。
4. 操作类权限（创建、编辑、删除、导出等）来自 `Permission` 表，并按 `module` 聚合到相应业务模块。必须先检查现有 `Permission.module`、`Permission.code`、`Menu.code` 和 `Menu.permissionCode` 的实际数据是否遵循同一套命名映射，不能通过字符串猜测把权限错误归到其他模块。
5. 组节点状态支持全选、部分选中（indeterminate）、未选中；勾选父节点应选择所有可分配的后代权限，取消父节点应取消其后代。若现有产品希望父节点仅控制菜单访问，则需显式定义为另一种行为，并在 UI 帮助文案说明，禁止出现没有一致语义的混合行为。
6. 默认提供搜索权限、全部展开、全部折叠、清空选择和已选择数量。
7. 搜索结果中保留父级路径，取消选择不能因为过滤而误删不可见的已选项。
8. “读取权限”和“更改权限”分开授权。只有具备 `roles.permissions.update` 的操作者才可保存；没有权限的用户只能查看或不能进入页面。
9. 页面进入时读取服务端现有权限并回显。保存成功后必须重新读取或使用服务端返回的规范结果校准 UI，不可只根据本地勾选数量显示成功。
10. 保存过程中禁用重复提交；保存失败保留当前未保存的勾选状态，并显示可重试错误。

## 3. 权限数据模型与一致性规则

当前初始 Prisma 模型已包含：

- `Role`：角色主档，含 `code`、`nameKey`、`description`、`isSystem`。
- `Permission`：稳定权限编码、翻译 key 和模块分类。
- `RolePermission`：角色与权限多对多关联。
- `UserRole`：用户与角色多对多关联。
- `Menu`：菜单树；具有 `code`、`parentId`、`route`、`permissionCode`、`visible`、`enabled`。
- `MenuTranslation`：菜单中英文名称。

因此，本次优先复用 `RolePermission` 作为授权数据源；不建议另建一套独立的 `RoleMenu` 来存相同的权限，否则会出现菜单显示授权与 API 授权不一致的风险。

### 3.1 推荐权威关系

- `Permission.code` 是授权判断的权威标识。
- `Menu.permissionCode` 可映射到页面访问权限 `Permission.code`。
- 操作权限以 `Permission` 为准，按模块分组显示。
- `RolePermission` 记录 roleId + permissionId，联合主键防止重复授权。
- 菜单是否可见、是否启用（`Menu.visible` / `enabled`）是菜单配置属性，不等同于角色权限。
- 有权调用 API 的最终判断必须在服务端基于当前登录人的有效权限进行；隐藏菜单/按钮不是安全措施。

### 3.2 实施前数据盘点

上线前生成只读报告，至少检查：

1. 每个非空 `Menu.permissionCode` 是否都能在 `Permission.code` 找到。
2. 是否存在未被任何菜单引用、但仍应作为按钮/接口权限存在的 `Permission`。
3. `Permission.module` 是否能稳定映射到业务菜单/模块。
4. `RolePermission` 是否存在已失效或重复数据（联合主键理论上应禁止重复）。
5. 所有用户所需的基础角色是否存在；`super_admin` 是否确实拥有全量所需权限。
6. `nameKey` 是否存在对应的翻译资源；当前 UI 显示 `role.sales` 这类字符串可能说明翻译 key 没有正常解析，应一并修复展示逻辑。

数据不一致时先写迁移/种子修正，再启用权限编辑器；不能让编辑器悄悄忽略找不到权限的菜单节点。

### 3.3 数据库是否需要修改

基本 CRUD 和 RolePermission 关系配置原则上不需要新表。但需要依据当前实际实现确定：

- 若角色中英文名称沿用 `nameKey` + i18n 文件，不需要数据库迁移，只修复显示与翻译资源。
- 若要求管理员从后台动态编辑每个角色的中英文名称/描述，应新增 `RoleTranslation` 表或等价多语言结构，并提供 Prisma migration、回填和回滚计划。
- 现有 `Role` 没有 `isActive` 字段。如果未来需要停用角色而非删除，可新增 `isActive Boolean @default(true)`；本次不要在 UI 假造一个数据库并不存在的启用状态。
- 不要为了显示权限树额外加 `RoleMenu`，除非技术审查证明现有 `Permission` 模型无法表达所需关系，并且已完成数据一致性设计。

## 4. API 设计建议

实施前必须优先检查现有 Controller、Service、DTO 和 API 命名；下面是推荐契约，不要求机械创建重复端点。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/admin/roles` | `roles.read` | 分页、关键词、角色类型筛选；返回用户数/权限数 |
| POST | `/admin/roles` | `roles.create` | 创建自定义角色 |
| GET | `/admin/roles/:id` | `roles.read` | 角色详情 |
| PATCH | `/admin/roles/:id` | `roles.update` | 修改名称、描述等可编辑字段 |
| GET | `/admin/roles/:id/permissions` | `roles.permissions.read` | 查询该角色当前权限 code 列表 |
| PUT | `/admin/roles/:id/permissions` | `roles.permissions.update` | 完整替换该角色授权集合，事务执行 |
| GET | `/admin/permissions/tree` | `roles.permissions.read` | 获取菜单/模块分组的可配置权限树 |
| GET | `/admin/roles/:id/users` | `roles.read` | 查看该角色关联用户，供删除保护与影响说明 |
| DELETE | `/admin/roles/:id` | `roles.delete` | 删除自定义且未分配用户的角色；系统端二次保护 |

### 4.1 列表参数和响应示例

请求：

```http
GET /admin/roles?page=1&pageSize=20&keyword=sales&type=custom
```

响应建议：

```json
{
  "items": [
    {
      "id": "role-uuid",
      "code": "sales",
      "name": "销售人员",
      "description": "负责客户询盘跟进",
      "isSystem": false,
      "userCount": 3,
      "permissionCount": 11,
      "updatedAt": "2026-10-15T19:00:00.000Z"
    }
  ],
  "page": 1,
  "pageSize": 20,
  "total": 1
}
```

分页、搜索字段需白名单化；对 code/name 使用受控的模糊搜索；后端设置 pageSize 最大值。

### 4.2 权限树响应示例

```json
{
  "items": [
    {
      "menuCode": "catalog",
      "labelKey": "menu.catalog",
      "children": [
        {
          "menuCode": "products",
          "labelKey": "menu.products",
          "accessPermissionCode": "products.read",
          "permissions": [
            { "code": "products.read", "labelKey": "permission.products.read", "module": "products" },
            { "code": "products.create", "labelKey": "permission.products.create", "module": "products" },
            { "code": "products.update", "labelKey": "permission.products.update", "module": "products" }
          ]
        }
      ]
    }
  ]
}
```

以上字段仅是契约示例。真实 `code` 和层级必须由现有数据库数据校准；不可将示例中的权限编码当作既有事实写进业务代码。

### 4.3 保存权限请求

```http
PUT /admin/roles/:id/permissions
Content-Type: application/json
```

```json
{
  "permissionCodes": ["products.read", "products.create", "customers.read"]
}
```

服务端必须：

1. 验证操作者登录状态和 `roles.permissions.update`。
2. 验证目标角色存在且不是受保护的系统角色。
3. 验证 `permissionCodes` 是字符串数组、没有重复项，数量在限制内。
4. 对所有 code 做数据库查询，拒绝任何不存在或不可分配的 code；不能静默忽略无效项。
5. 校验操作者是否有权分配这些权限。非超级管理员默认不得授予自己没有的权限，防止权限提升；超级管理员策略由后端明确实现。
6. 在事务内替换 `RolePermission` 集合。
7. 写审计日志，包含 actor、roleId、变更前后权限 code 差异和 requestId；不记录敏感 token。
8. 事务提交后失效权限缓存/会话中的权限快照；并发更新需考虑版本校验或以数据库最终状态为准。
9. 返回规范化的已保存权限列表或版本号。

### 4.4 错误码建议

| 错误码 | HTTP | 场景 | UI 处理 |
|---|---:|---|---|
| `ROLE_NOT_FOUND` | 404 | 角色不存在或已删除 | 关闭/刷新详情并提示 |
| `ROLE_SYSTEM_PROTECTED` | 409 | 尝试编辑/删除受保护系统角色 | 展示系统角色保护原因 |
| `ROLE_IN_USE` | 409 | 角色仍关联用户，不能删除 | 显示关联用户数和后续操作提示 |
| `PERMISSION_CODE_INVALID` | 400 | 提交不存在的权限 code | 保留勾选，提示刷新权限数据 |
| `PERMISSION_ASSIGNMENT_FORBIDDEN` | 403 | 操作者不能授予指定权限 | 不保存，显示无权分配提示 |
| `LAST_SUPER_ADMIN_PROTECTED` | 409 | 操作会导致无有效超级管理员 | 明确提示不可执行 |
| `CONCURRENT_ROLE_UPDATE` | 409 | 角色已被其他管理员修改 | 提示刷新后重新操作 |

实际项目已有统一错误码时应优先复用，不要创建重复体系。

## 5. 服务端业务规则与安全控制

### 5.1 角色创建

- 仅创建 `isSystem=false` 的自定义角色。
- `code` 必须唯一；建议格式 `^[a-z][a-z0-9_]{1,79}$`，后端二次校验。
- 不接受客户端提交 `isSystem=true`、用户数、权限数或其他计算字段。
- 新角色默认零权限，随后通过权限配置明确授予；如产品希望模板创建，必须通过经过服务端校验的 role template 实现，不能复制任意角色权限而不审计。

### 5.2 角色编辑

- 允许更改名称、描述；不允许普通编辑修改 `id`、`code`、`isSystem`。
- 修改角色详情和修改权限使用不同权限 code，防止只有只读角色信息权限的用户修改授权。
- 必须拒绝对 `isSystem=true` 的角色编辑基础信息或权限集合。

### 5.3 删除角色

- 仅删除 `isSystem=false` 且 `userCount=0` 的角色。
- 后端在事务中再次查询用户关联数，不信任前端传入的 count；若已有用户关联，返回 `ROLE_IN_USE`。
- 删除角色时可级联清理 `RolePermission`；是否保留历史审计记录由审计实体的关联设计决定，审计中应保留 role code/name 快照，避免删除后不可读。
- 前端二次确认，明确显示要删除的角色编码和名称。危险按钮放在操作列菜单或详情页，不与普通编辑按钮同色。
- 如果未来存在必须保留历史引用的合规要求，则改为停用方案；需新增字段和数据迁移，不能直接假设软删除已存在。

### 5.4 超级管理员保护

- `super_admin` 作为系统种子角色，应由 `isSystem=true` 或等价服务端规则保护。
- 禁止普通角色权限配置将超级管理员的权限集合清空或修改。
- 若存在“最后一个有效超级管理员”规则，必须在用户-角色分配、账号停用和角色删除等相关写操作中统一检查，避免只在用户管理页保护、从角色模块绕过。
- 权限更新 API 必须有对象级权限校验和角色保护，不能仅靠前端禁用保存按钮。

### 5.5 菜单权限与接口权限

- 后端 API 授权按 `Permission.code` 检查，不以 URL 路径、按钮是否隐藏或菜单是否可见代替。
- 角色权限变化必须更新权限缓存；缓存失效前应确保旧权限不会无限期可用。
- 用户有页面访问权限不代表可以执行创建、删除或导出等操作；读/写/删除/导出权限分离。
- 菜单 tree 仅返回可配置菜单和权限数据；是否返回隐藏菜单需结合产品规则决定，但隐藏系统菜单不应导致后端权限被删除。

## 6. 前端组件与状态要求

推荐组件边界：

- `RoleListPage`：筛选、分页、错误/空状态、列表刷新。
- `RoleFormDrawer`：创建/编辑基础信息。
- `RolePermissionDrawer` 或 `RolePermissionPage`：查看与配置权限树。
- `PermissionTree`：父子级勾选、indeterminate、搜索、展开/折叠。
- `RoleDeleteConfirmDialog`：危险操作确认。

状态至少包括：

- 页面：`loading`、`error`、`empty`、`success`。
- 表单：`initializing`、`submitting`、`fieldError`、`serverError`。
- 权限配置：`loadingTree`、`loadingGrantedPermissions`、`dirty`、`saving`、`saveError`。
- 列表按实际授权决定按钮；但隐藏按钮不替代服务端保护。

防止权限树常见 bug：

1. 父节点和子节点不能独立维护互相矛盾的勾选状态；以唯一 `Set<permissionCode>` 作为前端源状态，再推导父节点 checked/indeterminate。
2. 搜索过滤是视图过滤，不应覆盖完整 selected set。
3. 收到菜单树/角色权限两个 API 时，应在二者均成功后初始化编辑态；不能先默认全不选再异步覆盖，造成闪烁或误保存。
4. 没权限的用户不能通过复制 API 请求保存；服务端始终是最终授权点。
5. 保存成功后更新列表 `permissionCount`，不应要求用户手工刷新页面。

## 7. 国际化与视觉规范

- 页面必须沿用已有 Admin Shell、设计 Token、表格/Drawer/Modal/Toast 组件，不另建视觉风格。
- 翻译资源至少维护 `zh-CN` 和 `en-US`。
- 角色 code、permission code 和 API enum 是稳定机器标识，永远不翻译。
- `nameKey`、`labelKey` 用于读取翻译资源时，缺少翻译需要有清晰 fallback（例如显示 code 并记录开发日志），生产环境不应把 `role.sales` 作为用户可见名称而无提示。
- 角色权限树桌面端左右分栏；小屏改为单列折叠树/全屏 Drawer，不得出现不可操作的横向溢出。
- 所有复选框支持键盘操作、焦点可见和可访问名称；组节点部分选中状态正确暴露给辅助技术。

## 8. 测试与验收标准

### 8.1 功能验收

- [ ] 有 `roles.create` 权限的管理员可创建唯一 code 的自定义角色。
- [ ] 重复 code、空 code、非法 code、超长名称被前后端正确拒绝。
- [ ] 列表搜索 code/名称有效；类型筛选、分页总数正确。
- [ ] 编辑名称/描述成功且刷新后仍存在；code 和 `isSystem` 不可从普通编辑修改。
- [ ] 系统角色显示保护提示，不能编辑、删改授权或删除。
- [ ] 用户数大于 0 的角色删除会被前端阻止，并由后端返回 `ROLE_IN_USE` 作为最终保护。
- [ ] 用户数为 0 的自定义角色可确认删除；列表、权限关联和审计行为符合设计。
- [ ] 权限配置界面显示来自 API 的真实菜单/权限项，无硬编码假数据。
- [ ] 已有权限准确回显，父节点 checked/indeterminate 符合子项状态。
- [ ] 修改后保存成功，重新打开仍准确回显，列表权限数更新。
- [ ] 无效 permission code 或无权授予的权限提交失败，当前数据不会部分更新。
- [ ] 同时两名管理员修改一个角色时，最终状态和冲突反馈明确，不出现静默覆盖。
- [ ] 修改角色权限后，新权限立即按定义生效，旧权限缓存失效。

### 8.2 安全验收

- [ ] 未登录请求全部管理 API 被拒绝。
- [ ] 仅有 `roles.read` 的用户不能创建、编辑、删除或配置权限。
- [ ] 直接调用 DELETE 不能删除系统角色或被分配的角色。
- [ ] 直接调用 PUT 权限接口不能给自身授予不允许分配的权限。
- [ ] 不能通过修改 `isSystem`、roleId 或 permissionIds 绕过服务端校验。
- [ ] 最后一个有效超级管理员保护在相关入口一致有效。
- [ ] 审计日志记录角色创建、基础信息修改、权限差异和删除；无密码、token 或 session secret 泄漏。

### 8.3 UI 与兼容验收

- [ ] 桌面 1440px、笔记本 1280px、平板 768px、手机 390px/360px 可操作。
- [ ] 中英文切换后标题、字段、提示、空状态、错误信息均翻译；权限 code 不变。
- [ ] 权限 API 加载失败显示重试，不把页面显示成“没有权限”或自动清空。
- [ ] 保存中防重复提交；失败保留修改内容；成功有反馈并刷新权限数。
- [ ] 删除有确认弹窗；不可删除时说明原因，而不是无响应。

## 12. 本次明确的设计决定

1. **授权唯一来源是 `Permission` + `RolePermission`**，不重复引入独立角色菜单授权表。
2. **菜单和动作权限一起配置，但概念不同**：菜单 `permissionCode` 控制页面入口，操作权限控制具体 API/动作。
3. **系统角色只读**；自定义角色可维护。角色在用时先重新分配用户，不能直接删除。
4. **权限保存后端权威**：必须服务器校验、事务更新、审计和缓存失效。
5. **角色国际化先查清 `nameKey` 设计**，不在没有迁移方案的情况下把 key 字段直接改存显示文案。
