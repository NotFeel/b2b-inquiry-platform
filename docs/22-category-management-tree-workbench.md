# 22. 品类管理树形工作台：UI、技术与验收实施方案

> 适用页面：后台 `/zh-CN/categories`、`/en-US/categories`（具体路由以现有项目为准）  
> 目标：让运营人员能一眼查看并维护“五金工具、汽车用品、玩具、运动户外”等一级目录及任意层级子目录，并保证前台目录和产品筛选正确。  
> 重要约束：本文件是实施基线；正式编码前必须检查当前代码、API、迁移和数据，不得只按文档假定接口已存在。

---

## 1. 当前页面问题与目标

### 1.1 当前截图体现的问题

当前品类管理页只显示扁平表格，示例只有 `Industrial components (demo)` 一条记录。虽然表单已经有“上级品类”，但用户无法在主页面直观看出树状结构，也很难快速回答：

- 玩具下面有哪些细分品类？汽车用品下有哪些子分类？
- 当前选中节点位于哪条路径、属于哪一级？
- 一个目录有多少直接商品，连同下级一共有多少商品？
- 新增品类应当作为一级目录，还是某个目录的子目录？
- 停用/隐藏父品类会对前台子分类和产品造成什么影响？

当前右侧 Drawer 的字段虽有父级 UUID 输入概念，但用 UUID 文本让管理员填写不直观，也容易关联错误。应改为可搜索的树形下拉选择。

### 1.2 改造目标

1. 管理端以“左侧品类树 + 右侧所选品类详情和子品类列表”为主工作区。
2. 同时提供树形视图与列表/搜索结果视图；搜索能定位节点并展示完整祖先路径。
3. 新增一级品类和新增子品类的路径明确，父级通过树形选择器确定，绝不要求手填 UUID。
4. 支持不限固定两/三级的多层结构；运行时设置最大深度保护，默认业务建议不超过 8 层，最终以服务端配置为准。
5. 清楚区分 `enabled`（是否启用）与 `visible`（是否在前台显示），避免将两个业务含义合并。
6. 品类排序可控；默认先用同级上移/下移和数值排序，拖拽作为可选增强，不以拖拽作为唯一排序手段。
7. 删除与移动操作有服务端约束，不能让商品失去合法品类或制造循环引用。
8. 中后台支持 `zh-CN` / `en-US`，前台内容默认英文；语言字段必须来自翻译表，不在主表硬编码中英文列。

### 1.3 完成定义

- 页面打开后可查看完整品类树，支持展开、折叠、搜索、选择节点、显示当前路径。
- 创建“玩具”一级类目后，可继续创建“模型玩具”“电动玩具”等下级，并能看到清晰的缩进层级。
- 通过父级选择器新增节点；非法父级、重复 code/slug、移动到自身或后代等情况由前后端双重防护，后端为最终权威。
- 右侧详情有直接商品数和后代商品总数，两个指标定义清晰。
- 被子品类或产品引用的品类不能被直接物理删除；应提示改为停用/隐藏，或先迁移关联。
- 前台品类导航和品类筛选使用相同的目录数据与可见性规则；点击父级能够进入包含后代产品的目录结果。

## 2. 页面 IA 与布局规范

### 2.1 推荐主界面

桌面端使用全宽工作台布局，保留系统统一的 Admin Shell（侧栏、顶栏、面包屑）。主内容建议如下：

```text
┌─────────────────────────────────────────────────────────────────────────┐

├────────────────────────────────┬────────────────────────────────────────┤

│                                │ 路径：全部品类 / 玩具                         │
│ ▾ 五金工具      12 类 / 78 商品  │ Code: toys     Slug: toys                    │
```

以上为布局示意，不是现有数据截图。实际树节点、商品数、code 和名称全部由 API 返回，不得用演示值冒充生产数据。

### 2.2 推荐尺寸

- 内容区：使用后台通用页面容器，不改变 Admin Shell。
- 左侧树面板：宽度 `300–360px`，桌面端可拖动调整，最小 `260px`、最大建议 `440px`。
- 右侧详情区：`min-width: 0; flex: 1`，允许表格正常缩放。
- 两面板间距：`16–20px`；面板内边距：`16–20px`。
- 树节点高度：`36–42px`；层级缩进：每层 `16–20px`；图标和文字垂直居中。
- 主按钮只保留一个主要动作“新建一级品类”；子节点通过“新增子品类”进入，防止新增路径含糊。
- 详情右上角主动作按权限显示：`编辑`、`新增子品类`、`更多`；删除放到更多菜单并使用危险操作样式。

### 2.3 页面顶部工具栏

建议提供：

- 标题“品类管理”和简短说明；
- `+ 新建一级品类`；
- 搜索框：按中文/英文名称、code、slug 搜索；
- 状态筛选：全部、启用、停用；
- 前台显示筛选：全部、显示、隐藏；
- 可选“只看有商品”“只看空品类”；
- “展开全部 / 折叠全部”；
- 若规模足够大，再增加“树形视图 / 列表视图”切换。

不需要一开始加入复杂仪表板或过多统计卡。主任务是找目录、理解层级、维护父子关系。

### 2.4 左侧品类树行为

每个节点显示：

- 展开/折叠按钮（仅当有子节点时）；
- 品类图标或默认文件夹图标；
- 当前 locale 的名称；
- 可选小徽标：停用、前台隐藏；
- 商品数量建议放在 hover/详情，不要让每个节点同时显示过多数据。
- 节点右侧省略号菜单（有权限时）：新增子品类、编辑、向上/向下排序、复制 slug（如有需要）、停用/隐藏、删除。

交互规则：

1. 单击节点选择它；单击展开图标只展开/折叠，不切换选择。
2. 当前节点以明显但克制的底色/左侧标记突出；键盘焦点单独可见。
3. 默认展开所有一级目录；深层分支默认折叠，以免树过长。也可以记住用户本次会话的展开状态。
4. 搜索命中子节点时，自动展开祖先路径，并高亮命中名称；清空搜索后恢复之前的展开状态。
5. 搜索结果仍显示面包屑路径，例如 `商品目录 / 玩具 / 模型玩具`，不应只显示孤立的名称。
6. 当前选中节点被停用/隐藏时，仍能在后台树中查看和编辑（权限控制除外）；前台只按发布规则筛选。
7. 树为空时显示空状态和“新建一级品类”；加载失败时保留页面壳层并显示重试，而不是白屏。

### 2.5 右侧详情区

没有选中节点时显示引导：“从左侧选择一个品类，或新建一级品类”。

选中节点后展示：

- 本地化名称、完整祖先路径、code、slug；
- 父级品类；
- 当前状态：启用/停用、前台可见/隐藏；
- 描述、封面图（有值时）；
- 直接关联商品数；
- 含所有后代的商品总数（单独标注，不能与直接数混淆）；
- 创建时间、最近更新时间（若 API 返回）；
- 子品类列表（名称、code、slug、直接商品数、状态、前台可见性、排序、操作）。

子品类表为空时提示“该品类尚无子品类”，并提供“新增子品类”。不以空白区域代替明确空状态。

### 2.6 列表视图/搜索结果视图

树形界面是主工作流，但当用户搜索或需要批量核查时，可以提供列表视图：

- 列：品类名称（含层级路径）、code、slug、父品类、直接商品数、启用状态、前台可见性、排序、操作。
- 默认按层级路径、同级 sortOrder 稳定排序。
- 支持服务端分页、筛选和排序；避免把大量目录全塞进一个无分页表格。
- 从列表点击名称，应选择该节点并尽量展开/定位左侧树中的对应路径。

## 3. 新建/编辑 Drawer 设计

### 3.1 入口与上下文

- “新建一级品类”：打开 Drawer，父品类为空；标题“新建一级品类”。
- 选中某节点点击“新增子品类”：自动把当前节点写入父品类字段；标题“新增子品类”。
- 在全局工具栏点击“新建品类”：允许用户选择父品类，默认为一级目录。
- “编辑”：加载真实详情；所有已有值必须回显，加载失败时不能出现空表单让用户误保存。
- 创建和编辑共用表单组件，但字段权限不同。

### 3.2 字段规范

| 字段 | 类型 | 必填 | 规则 |
|---|---|---:|---|
| code | 文本 | 是 | 稳定机器编码，唯一；创建后默认不可编辑。建议小写字母、数字、连字符/下划线；按现有约束执行。 |
| slug | 文本 | 是 | 前台 URL 标识，全局唯一；规范化后校验。更改时提示会影响旧链接/SEO，推荐提供重定向或禁止直接更改已发布品类 slug。 |
| 父品类 | 可搜索树选择器 | 否 | 空表示一级品类；禁止选自身或任意后代；不允许粘贴 UUID 代替名称选择。 |
| 名称 | 多语言输入组 | 是 | 最少 `zh-CN`、`en-US`；中英文名称独立存入翻译表。 |
| 描述 | 多语言文本域 | 否 | 可用于前台品类介绍；按纯文本或安全富文本策略存储。 |
| 封面图片 | 资源选择器/上传 | 否 | 复用现有文件/图片上传服务；不直接存任意外部 URL。 |
| 排序 | 整数 | 是/默认 | 默认为同级最大 sortOrder + 10（或项目既定策略）；非负整数，排序只影响同级。 |
| 启用 | Switch | 是 | `enabled`；停用表示不允许正常业务使用/前台访问，具体传播规则按下文统一。 |
| 前台显示 | Switch | 是 | `visible`；决定该节点是否出现在公共导航/目录入口。与 enabled 分开。 |

### 3.3 `enabled` 与 `visible` 的传播策略

推荐统一规则：

- `enabled=false`：节点不出现在公共品类树、不接受新商品关联；其后代在前台也不可见，避免前台导航出现孤儿节点。后台仍可查看和修复。
- `visible=false`：该节点不作为前台导航入口展示，但如果业务允许“隐藏父节点、仍展示子类”，必须另行明确；默认建议父节点隐藏时整条分支不显示，避免用户无法从导航抵达子分类。
- 商品公开查询必须确认从根到当前品类的所有祖先都 enabled 且符合可见规则；不能仅检查叶节点。
- 如果运营确实需要隐藏父级但保留子级在前台，可增加明确的 `publicNavigationMode` 业务规则，而不是让前后端各自猜测。

### 3.4 表单校验与保存反馈

- code、slug 唯一性应由后端唯一索引/约束保证，前端可以先校验但不能代替服务端。
- 至少一门必需语言名称不能为空；推荐英文名称为前台必填，中文名称为后台当前管理语言必填，最终以业务决定为准。
- 父级选中项显示名称与完整路径，例如“商品目录 / 玩具”，不显示裸 UUID。
- 选择父级后即时校验最大深度及是否会形成循环；保存时后端再次校验。
- 保存时按钮进入 loading，阻止重复提交；成功后关闭 Drawer、刷新树和详情、保持当前选中节点合理；失败保留填写内容并显示字段级错误。
- 关闭含未保存变更的 Drawer 时弹出确认；没有改动时直接关闭。
- 禁用控件必须说明原因，不要只让控件灰掉。

## 4. 现有数据模型核查与推荐约束

当前文档基线 `database/prisma/schema.prisma` 已有以下结构（开发前请以仓库实际 schema 和数据库迁移为准）：

- `Category`: `id`、`code`、`slug`、`parentId`、`sortOrder`、`enabled`、`visible`、`coverAssetId`、时间字段；自关联 `parent/children`；与 `Product` 关联。
- `CategoryTranslation`: `categoryId`、`locale`、`name`、`description`，复合主键 `[categoryId, locale]`。
- `Product.categoryId`：商品直接关联一个品类，外键删除策略为 Restrict。

因此，本次主改造优先是 UI、查询和 API 完善，不应无理由再建一张“品类树表”或把中英文名称添加到 Category 主表。

### 4.1 必须确认的数据库约束

1. `Category.code` 全局唯一。
2. `Category.slug` 全局唯一（如未来要多站点/多语言 slug，需另立设计；当前默认全局唯一）。
3. `CategoryTranslation` 对每个 category + locale 只有一条记录。
4. `parentId` 必须引用存在品类；根节点 `parentId=null`。
5. `parentId` 自关联采用 Restrict，避免数据库级联删除子树。
6. 删除品类不能级联删除 Product；现有 `Product.category` 的 Restrict 约束应保留。
7. 查询路径、后代商品统计和排序需有索引策略；现有 `[parentId, sortOrder]` 索引可支持直接子节点查询。
8. 额外数据库字段仅在发现缺少必要能力后再添加；任何 schema 变更必须提供迁移和回滚。

### 4.2 深度和树完整性

- 最大层级建议配置为 `CATEGORY_MAX_DEPTH=8`，或者使用数据库/应用现有的集中式业务配置；不得在多个 UI/Service 中硬编码不同数值。
- “根节点深度”为 1。创建/移动前计算新深度：`parentDepth + 1 + subtreeHeight` 不得超过最大值。
- 后端更新父节点时，必须检测目标父节点是否为当前节点或当前节点的后代。
- 所有节点的 parent-child 变化放在事务中完成；并发移动可能形成环时，需使用事务隔离/行锁或基于版本的冲突检测。
- 如以后出现数万级节点，再评估 closure table / materialized path；当前模型默认 adjacency list（parentId），不为尚未出现的规模提前引入新模型。

## 5. API 契约建议

> 以下为建议契约。先对照当前 API 目录，复用已存在的路由、分页格式、异常结构与权限码；不要在没有检查的情况下平行创建重复 endpoint。

### 5.1 管理端 API

| 方法 | 路径示例 | 用途 | 权限建议 |
|---|---|---|---|
| GET | `/api/admin/categories/tree?locale=zh-CN&includeDisabled=true` | 获取完整树/可筛选子集 | `category.read` |
| GET | `/api/admin/categories/:id` | 读取详情、翻译、计数和路径 | `category.read` |
| GET | `/api/admin/categories/:id/children` | 读取直接子品类，分页可选 | `category.read` |
| GET | `/api/admin/categories` | 搜索/列表分页 | `category.read` |
| POST | `/api/admin/categories` | 创建品类 | `category.create` |
| PATCH | `/api/admin/categories/:id` | 更新名称、描述、slug、父级、排序等 | `category.update` |
| POST | `/api/admin/categories/:id/move` | 将节点移动到新父级并调整顺序（若拆分该操作） | `category.update` |
| POST | `/api/admin/categories/reorder` | 批量更新同级排序（可选） | `category.update` |
| PATCH | `/api/admin/categories/:id/status` | 启用/停用、前台可见性变更（如拆分） | `category.update` |
| DELETE | `/api/admin/categories/:id` | 删除无子节点、无商品引用的品类 | `category.delete` |

具体路由与权限码必须以项目现有命名体系为准。

### 5.2 树节点响应结构示例

```json
{
  "id": "uuid",
  "code": "toys",
  "slug": "toys",
  "name": "玩具",
  "locale": "zh-CN",
  "parentId": null,
  "sortOrder": 20,
  "enabled": true,
  "visible": true,
  "directProductCount": 4,
  "descendantProductCount": 27,
  "children": []
}
```

- `directProductCount` 只统计直接 `categoryId` 等于当前节点的商品。
- `descendantProductCount` 统计当前节点及其所有后代品类关联的商品总数；必须明确是否含自身，上述命名建议不含自身，另用 `totalProductCount` 表示含自身。如果接口选用 `descendantProductCount`，则不得又把自身包含进去。
- 推荐统一返回 `directProductCount` 与 `totalProductCount`，避免命名歧义：`totalProductCount = direct + all descendants`。
- 管理端可包括停用/隐藏节点；公共端不能直接复用管理端响应 DTO。
- 翻译缺失时服务端按 `requested locale → en-US → zh-CN → code` 回退；必须返回 `resolvedLocale`（可选）或在 API 文档中固定此规则，并在管理 UI 标记缺失翻译。

### 5.3 列表/搜索响应

建议采用统一分页响应：

```json
{
  "items": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

过滤参数使用白名单：`q`、`parentId`、`enabled`、`visible`、`hasProducts`、`locale`、`page`、`pageSize`。`pageSize` 有最大值，例如 100。

### 5.4 写入请求示例

```json
{
  "code": "model-toys",
  "slug": "model-toys",
  "parentId": "parent-uuid",
  "sortOrder": 10,
  "enabled": true,
  "visible": true,
  "coverAssetId": null,
  "translations": [
    { "locale": "en-US", "name": "Model Toys", "description": "" },
    { "locale": "zh-CN", "name": "模型玩具", "description": "" }
  ]
}
```

服务端只接受明确定义的 DTO 字段；不能允许客户端提交并覆盖 `id`、`createdAt` 等系统字段。`code` 即使从编辑请求中被提供，也应拒绝修改或忽略并返回明确校验响应，具体策略统一在 API 规范中定义。

## 6. 后端实现策略

### 6.1 Service 边界

建议在现有后端框架中实现/完善 `CategoryService`，按项目惯例拆分：

- `getTree(locale, includeDisabled, filters)`：读取节点与翻译，构造树；
- `getDetail(id, locale)`：详情、breadcrumb、计数、直接子项；
- `create(dto, actor)`：校验父级、深度、唯一性、翻译、权限，事务创建；
- `update(id, dto, actor)`：变更普通字段与翻译；如果父级变化，要执行完整树检查；
- `move(id, targetParentId, sortOrder, actor)`：可独立出来处理树移动；
- `delete(id, actor)`：校验子节点、商品关联、系统保护规则；
- `getPublicTree(locale)` / `getPublicCategoryProducts(slug, filters)`：独立公共查询逻辑，不能把 admin DTO 直接返回前台。

Controller 只负责路由、身份、DTO 解析和统一响应；不要把递归树逻辑写在 Controller 中。

### 6.2 构造树的算法

若一次读取全部节点：

1. 以 `id` 建立 `Map<CategoryId, Node>`；
2. 所有节点先初始化 `children=[]`；
3. 对每个节点检查 `parentId`；父节点存在则推入父节点 children，否则作为 root（异常 parentId 应记录诊断日志并触发数据一致性告警，不能静默忽略）；
4. 每级按 `sortOrder ASC, name ASC, id ASC` 稳定排序；
5. 附加当前语言名称、直接商品数、总商品数、当前路径等字段；
6. 返回树。

时间复杂度应接近 `O(n)`（排序之外），禁止对每个节点分别请求子节点或商品计数导致 N+1 查询。

### 6.3 计数避免 N+1

- 直接商品数：按 `categoryId` 分组聚合一次。
- 总商品数：对节点构建后按后序遍历累计当前节点 `directProductCount + sum(children.totalProductCount)`。
- 若使用数据库递归 CTE，也需保持数据库方言与项目 ORM 策略一致；不要为了一个计数引入不可维护的原始 SQL。
- 对启用/停用、草稿/发布产品是否计入后台统计，默认后台“关联商品数”统计所有商品记录；若需要展示“公开商品数”，需使用另一明确字段/筛选，避免混淆。

### 6.4 分类树读取策略

MVP 建议一次读取轻量字段和翻译，适合中小规模目录；如果品类超过可配置阈值（例如 2,000 节点），改为按父节点惰性加载，但 API 和 UI 需统一支持 `childrenLoaded` / `hasChildren`，并保持搜索可跨树定位。

无论采用哪种策略：

- 树节点响应不要携带大量商品详情，只携带计数；
- 树接口必须受管理端权限保护；
- 搜索与列表分页在服务端执行；
- 缓存需要在创建、编辑、移动、启停、删除时失效。

### 6.5 删除保护

后端删除顺序：

1. 校验 `category.delete`；
2. 查询并锁定目标品类（事务内）；
3. 若有子品类，返回 `CATEGORY_HAS_CHILDREN`；
4. 若有关联商品，返回 `CATEGORY_HAS_PRODUCTS`；
5. 若有外部引用（导出模板筛选、运营活动或其他模块的显式外键/配置），根据实际数据模型阻止删除或先迁移引用；
6. 删除翻译和品类记录，写审计日志并失效缓存。

推荐默认阻止物理删除，不自动删除/移动商品。UI 提供“停用”或“前台隐藏”作为安全替代方式；需要调整商品归属时使用专门的批量迁移流程。

### 6.6 移动与循环检查

保存 `parentId` 之前必须：

- 验证新父节点存在且允许作为父品类；
- `targetParentId !== id`；
- 遍历 targetParent 的祖先链，不能遇到当前 id；
- 检查移动后整棵子树不会超过最大深度；
- 如同时更新同级顺序，用事务统一处理。

不能仅靠前端隐藏“当前节点及后代”来防止循环；后端必须独立验证。

## 7. 前台品类导航与商品筛选的联动规则

### 7.1 公共品类树

前台只展示满足公共可见规则的节点：

- `enabled=true`；
- `visible=true`；
- 自己与必要祖先链均符合公开规则；
- 当前 locale 有可回退的翻译；
- 不返回后台内部字段或敏感信息。

公共树应独立 DTO，字段最少化：`id/code/slug/name/children`（以及产品数量是否公开由产品需求决定）。不要复用含管理审计和内部状态的后台 DTO。

### 7.2 点击父类目的筛选

默认策略：用户点击某个目录时，查询该节点以及其所有后代节点中的可公开商品。具体包括：

- 只返回已发布且允许公开的产品；
- 排除草稿、已下架、已停产等不公开状态；
- 查询参数不能由客户端任意指定 SQL 字段；
- 品类路径使用 slug 路由并生成 breadcrumb；
- 如类目无商品，显示空状态、下级品类入口和全局搜索，不显示报错。

### 7.3 路由与 slug 变更

- `slug` 是 SEO/路由标识，不是数据库主键。
- 对已有公开流量的 slug 不建议随意修改；可采用锁定字段或在改 slug 时生成旧 slug → 新 slug 的重定向记录（如果当前项目已有 redirect 模型则复用）。
- 未实现重定向表前，至少弹出明确二次确认并记录审计，不能静默断链。
- 前台 API 应支持稳定的 slug 查找，不从用户输入的名称直接拼接路由。

## 8. 权限与审计

建议权限编码（需复用项目现有权限编码体系）：

- `category.read`
- `category.create`
- `category.update`
- `category.delete`
- `category.reorder`（若项目采用独立排序权限）
- `category.publish` 或 `category.visibility.update`（是否拆分由现有 RBAC 颗粒度决定）

安全规则：

1. 不同操作分别执行服务端权限验证；隐藏按钮不构成安全控制。
2. 修改 parentId、slug、enabled、visible、翻译、排序属于不同敏感程度，审计中记录具体差异，但不记录不必要的全部内容。
3. 删除、停用、改 slug、移动有大量后代/产品的品类需二次确认，并显示影响范围。
4. 操作者不能通过构造 API 请求绕过最大层级、唯一性、循环检查和删除保护。
5. 审计记录包含操作人、目标 categoryId、操作、时间、requestId、关键字段 before/after（避免把长描述/富文本全文塞进审计）。

## 9. 前端组件与状态设计

### 9.1 建议组件拆分

依现有 React/Next.js 代码约定复用/创建：

- `CategoryManagementPage`：页面编排、查询参数、选中节点；
- `CategoryTreePanel`：树视图、节点搜索、展开折叠；
- `CategoryTreeNode`：递归节点；使用稳定 `key=category.id`；
- `CategoryDetailPanel`：详情摘要与操作入口；
- `CategoryChildrenTable`：直接子品类表格；
- `CategoryFormDrawer`：创建/编辑统一表单；
- `ParentCategoryTreeSelect`：搜索式树形父级选择器，支持排除自身和后代；
- `CategoryStatusBadge`：启用/停用与前台可见/隐藏状态；
- `DeleteCategoryDialog`：显示删除前影响检查。

不要在本页复制另一份颜色、按钮、Drawer 和表格样式，应复用共享 UI package/现有 Design Tokens。

### 9.2 状态管理建议

最少需要维护：

- `treeData`、`treeLoading`、`treeError`；
- `selectedCategoryId`；
- `expandedIds`；
- `searchQuery` 与 filter state；
- `drawerMode = createRoot | createChild | edit`；
- `formDirty` / `saving`；
- `pendingAction` / `deleteCheck`。

不要直接把整棵树和表格各自维护成两份可写数据；以 API query cache 为数据源，变更成功后执行统一失效/更新。浏览器刷新后可以通过 URL `?selected=<id>`（如果合适）恢复选中节点，但不得把未授权的内部信息放进 URL。

### 9.3 加载/错误/空状态

- 初次加载：树和右侧详情分别显示 skeleton，不让整个后台空白。
- tree 加载失败：显示错误说明与重试按钮，保持 Admin Shell。
- 搜索无结果：显示清空搜索入口。
- 无选中项：显示引导空状态。
- 节点无子类：显示“暂无子品类”，同时保留新增子类动作。
- 保存失败：保留表单值，显示 field error/toast；禁止清空后让用户重填。
- 数量统计暂不可用：显示 `—` 并提示刷新，不要编造 0。

- 状态不能只通过颜色表达，需要文字标签；
- 删除确认对话框打开后管理焦点，关闭后返回触发按钮。

## 11. 性能、缓存与可靠性

1. 树接口只返回必要字段和计数，不携带产品明细。
2. 避免 N+1：翻译、直接商品数必须批量查询/聚合。
3. 对树搜索使用服务端过滤和合理索引；`q` 使用参数化查询。
4. 目录数量较小时可以一次加载；超过阈值切换惰性加载，不要无条件增加复杂缓存。
5. 在创建、更新、移动、排序、启停、可见性变化、删除后失效：管理端树缓存、公共品类树缓存、相关品类产品列表缓存和必要的 SSR/ISR 缓存。
6. 缓存键应包含 locale 和公开筛选条件；后台数据不能混入公共缓存。
7. 多人同时维护同一节点时，采用 `updatedAt`/版本字段做乐观并发校验；如 schema 不增加版本字段，可以基于更新前 `updatedAt` 检查并返回 409 冲突。
8. API 错误返回稳定错误码，如 `CATEGORY_CODE_EXISTS`、`CATEGORY_SLUG_EXISTS`、`CATEGORY_HAS_CHILDREN`、`CATEGORY_HAS_PRODUCTS`、`CATEGORY_TREE_CYCLE`、`CATEGORY_MAX_DEPTH_EXCEEDED`、`CATEGORY_CONCURRENT_UPDATE`。

## 14. 回滚与风险控制

- UI 改造优先通过新增页面组件与现有 API 适配层完成，避免无关重构 Admin Shell。
- API 变更保持向后兼容；先新增/扩展树接口，再切换前端，确认无旧调用后再考虑清理旧接口。
- 若需要数据库变更，遵循 additive migration；先备份、迁移、验证计数，再切换读写，禁止直接改生产表。
- 数据移动/批量重排要在事务中执行，并记录移动前后的 parentId/sortOrder，以便审计与人工恢复。
- 旧数据中若发现孤儿节点、重复 slug、超过最大深度或缺失翻译，先生成诊断报告，不自动删除/改名；修复方案经业务确认后再执行。
- 回滚 UI 时保留新增 API 不影响旧页面；回滚数据迁移需有明确逆向步骤，不能假定任意迁移都可自动逆转。

## 16. 本次技术结论

本次需求的关键是把当前“平铺品类列表”改为“可以理解和管理层级关系的树形工作台”，而不是简单把父级字段换成下拉框。当前基线数据模型已经支持 `parentId` 自关联、多语言翻译、排序、启用/可见状态和商品关联，因此首选方案是复用现有模型，优先补齐树接口、统计和安全校验，再重构 UI。

最终验收要以真实数据闭环为标准：管理员创建一级“玩具”，再新增“模型玩具”“电动玩具”，修改中英文名称和排序，刷新后树结构一致；前台目录正确展示，点击父类目能筛选后代商品；删除有子节点/商品引用的品类时后端可靠拒绝。
