# Category Management Skill — 品类树管理强制规范

执行品类管理任务前，必须阅读 `AGENTS.md`、`docs/01-product-requirements.md`、`docs/06-admin-public-ui-standard.md` 和 `docs/22-category-management-tree-workbench.md`。

## 必须遵循

1. 首先检查现有 `Category`、`CategoryTranslation`、`Product.categoryId`、迁移和现有 API。默认复用 `parentId` 自关联和翻译表，禁止未经审查新建第二套品类/分类数据模型。
2. 后台品类主工作区采用可搜索的左侧树 + 右侧详情/子品类列表。必须支持展开/折叠、路径、空状态、加载错误、状态标识与中英双语。
3. 新建一级品类、新增子品类、编辑复用统一表单。父品类必须通过树形选择器选择，不允许手填 UUID。当前节点及其后代不得成为其新父节点。
4. `code`、`slug` 唯一性必须由数据库约束和服务端校验共同保证。对已发布 slug 的修改必须考虑 SEO 旧链接；不可静默断链。
5. 服务端必须校验父节点存在、树循环、最大层级、同级排序合法性、操作者 RBAC 权限和并发更新冲突；不能只依赖前端控件过滤。
6. 删除有子节点或产品引用的品类时应阻止物理删除；不能级联删除 Product。默认优先建议停用/隐藏或通过明确流程迁移产品关联。
7. 明确区分 `enabled` 和 `visible`。后台可查看停用/隐藏节点；公共品类树与产品查询必须统一处理父节点/祖先链状态，不能只检查叶节点。
8. 详情同时区分直接商品数与含后代商品的总商品数。禁止 N+1 统计；翻译、商品计数需批量查询/聚合。
9. 树/详情/CRUD/排序 API 必须服务端鉴权；前端隐藏按钮不能替代 API 权限校验。建议复用项目现有 `category.read/create/update/delete` 权限码。
10. 所有写操作按项目规范审计并失效管理端树、公共品类树及相关产品列表缓存；翻译要按 locale 管理，至少支持 `zh-CN` 和 `en-US`。
11. 不因 UI 改造而随意改变数据库。任何 schema 变更必须伴随版本化 migration、数据回填核对和回滚方案。
12. 测试至少覆盖新增根/子品类、编辑双语字段、搜索定位、排序、重复 code/slug、最大深度、循环、删除保护、权限拒绝、停用/隐藏传播、前台后代筛选和 360px 响应式布局。
